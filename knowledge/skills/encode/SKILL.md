入力は、承認された学びのタスクである。
承認とは、人間がプールの一件を `todo` に上げたこと、または `procedures/harness-change` の手順 2 で承認を得たことを指す。
事例の件数で起票を絞るのは `skills/extract` の手順 5 だけで、承認された学びは件数に依らず適用する。
タスクの形（事例の id、破られた知識ファイルの参照キー）は `skills/extract` の手順 5 が決めている。

## 1. 事例を確かめる

1. `tools/learning/case list --pattern <pattern>` を実行する。事例は gori の git の共通ディレクトリの下の `gori/learning/` にあるので、`--root` を省いても、`--root` に本体のチェックアウトか worktree を渡しても、同じ事例を読む。
2. タスクに挙がっていて一覧に出ない id は取り消してあるので、根拠にしない。理由は `case retracted` で読める。
3. 残った事例の `gori/learning/cases/<id>.md`（git の共通ディレクトリの下）を読み、何が起きたかと、何が正しかったかを一文ずつ書く。

## 2. 定着の形を選ぶ

次の段を `criteria/encode-in-structure` の順で検討する。
選んだ段と、上の段で表せなかった理由を一文ずつ書き残す。

- **構造**：誤りが起きえない設計にする。状態の持ち主を一つにする、古い道を消す、など。
- **型と検査**：誤りを書けないようにするか、書いたら検査（`tools/knowledge/lint` の規則、道具の検査）が落ち、その失敗の出力が直し方を示すようにする。
- **テスト**：振る舞いが壊れたら落ちるテストを足す。
- **文章**：判断が要り、上の三つで表せないものだけを、手順書か判断基準に書く。

破られた知識ファイルが既に同じ指示を文章で持っているなら、文章をもう一度書かない。
文章では守られなかった証拠なので、上の段で表す。

構造、型と検査、テストは `tools/` の変更になる。
知識ファイルの変更と同じく `procedures/learning-apply` の手順で行い、知識ファイルの変更とは別の作業に分ける。

## 3. 足した検査が誤りで落ちることを示す

検査かテストを足したら、根拠の事例の誤りを再現する入力（フィクスチャ、一時リポジトリ）を作り、その入力で検査が落ちることをテストで確かめる。
同じ入力が、検査を足す前の main では通ることも確かめる。
どの事例の入力でも落ちない検査は足さない。

## 4. 来歴を書く

適用した知識ファイルの provenance を次のように書く。

- **source**：知識ファイルを新しく作るなら「学び: <pattern>」と書く。既存の知識ファイルに足すなら変えない。
- **patterns**：学びの pattern を足す（既にあれば足さない）。事例の id は書かない。事例はマシンの手元にしかなく、別のマシンでは指す先が無いためである。
- **enforced_by**：足した検査を `lint:<rule-id>`、`test:<テストファイルの名前>`、`verdict:<検査>`、`log:<検査>` の形で足す。検査を足さなかったら変えない。

## 5. 要らなくなった文章を探す

構造か検査で誤りが起きえなくなったら、同じ誤りを防ぐために書かれた文章を探す。
破られた知識ファイルの本文と、patterns に同じ pattern を持つ知識ファイルが候補である。
見つけた文章は消す案として人間に示し、知識ファイルごとの別の変更にする。

## 6. 適用せずに返すとき

次に当たったら、何も変えずに理由を書いて人間に返す。

- 学びが既存の知識ファイルの規則と矛盾する。
- 文章でしか表せず、文章では効き目が期待できない。
- 1 で根拠に残った事例が無い。
