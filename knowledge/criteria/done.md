**実物**：動いているシステム、実際に実行したコマンドの出力、実際に作られたファイル。
確認が失敗したら、仕組みを疑う前に、確かめ方を疑う。

重要なレビューは、その成果を作っていない者が下す。
**重要なレビュー**：成果を他者に渡す前（PR の作成、マージ、リリース）の合否のレビュー。
commit を伴わず、成果を他者に渡すかを人間が自ら決める作業（例：人間が submit する pending review）では、独立レビューのレビュー結果を求めない。
道具の照合の出力など実物での確認を、判断の記録の証拠に残して完了とする。
作業者は変更を commit してから、レビューを依頼する。

```
${CLAUDE_PLUGIN_ROOT}/tools/records/review --task <作業ID>
```

道具が HEAD の commit を、別のセッションのレビュアー（`agents/reviewer`、作業者と別のモデル）にレビューさせ、レビュー結果をその commit の SHA に結びつけて記録する。
道具は、レビューする範囲の差分のファイルから、レビューの重さを決める。作業者は重さを選ばない。
変えたファイルがすべて、振る舞いに効かない文書（`*.md` のうち、`knowledge/`、`agents/`、`hooks/`、`tools/`、`tests/`、`.claude/`、`.claude-plugin/` の下（入れ子のフォルダも含む）と `CLAUDE.md`、`AGENTS.md` を除くもの）なら軽い（light）にし、`config/models` の reviewer-light のモデルで、書いた事実と受け入れ基準に絞って確かめさせる。テストは全部は走らせない。
それ以外と、`--e2e` を付けた依頼は、ふつう（normal）である。決めた重さはレビュー結果の `weight` と判断の記録のレビュー結果の行に残り、`tools/learning/metrics` の `review-light` で数えられる。
レビューする commit がローカルの main（無ければ master）の先端を含まなければ、道具はレビュアーを起動せず終了コード 2 で止まる。
レビューした commit がそのまま fast-forward で main に入るようにするためである。
main の最新は `${CLAUDE_PLUGIN_ROOT}/tools/repo/sync-main --task <作業ID>` で取り込む。rebase か merge か、origin をどう扱うかは道具が決める。
道具が `UPSTREAM_DIVERGED=` を出したら、完了の報告で、上流（origin）と分かれていることを人間に伝える。
レビューを受けた commit は、レビュー結果が SHA に結びついているので、手で `rebase`、`commit --amend`、`reset` をして書き換えない。
道具が終了コード 1（衝突）で止まったら、衝突を解いて続ける。解くのに受け入れ条件の外の判断が要るなら、`--abort` で戻して人間に尋ねる。終了コード 2 なら、出力を人間に示して止まる。
取り込んだら検証をやり直し、`verdict check --task <作業ID>` を実行する。合格した commit に main を自動で取り込んだだけで、作業と main の変えたファイルが重ならなければ、道具が前の合格を引き継いで 0 を返すので、レビューに出し直さない。
0 でなければ `review --base <main>` で依頼する。付けないと、他の作業の変更までレビューの範囲に入る。
レビュアーは作業リポジトリに書けず、レビュー結果は道具が渡した受け取り口に書く。道具は、レビュアーのセッションと作業と SHA を確かめたレビュー結果だけを取り込む。
受け入れ条件が claude を起動する E2E（`tests/e2e/*.sh`）の通過を含むなら、`--e2e <リポジトリからの相対パス>`（複数可）を付ける。レビュアーのサンドボックスの中では claude を起動できないので、道具がレビューする commit の別の一時 worktree でサンドボックスの外でそのスクリプトを走らせ（時間の上限は既定 30 分、`GORI_E2E_TIMEOUT_SEC`）、終了コードと全出力をレビュアーに渡す。レビュアーはスクリプトの差分も読んで、検査が甘くなっていないかを確かめる。
人間が端末から（セッション ID の環境変数が無いこと。作業者のセッションは記録できない） `${CLAUDE_PLUGIN_ROOT}/tools/records/verdict record --task <作業ID> --result pass|fail` でレビューしてもよい（pass には `--evidence`、fail には `--finding` を付ける）。
疑似端末を作って人間を装う、レビュー結果のファイルを記録の場所（gori のチェックアウトの `.git/gori/repos/<名前>/verdicts`）に手で置く、レビュアーの起動に偽の claude を差し込む、のはどれも意図的な回避であり、この仕組みは防がない。
作業者はレビュー結果を書かず、書き換えない。
合格に、直すことを勧める指摘が添えられていれば（`verdict check` の出力に出る）、完了の報告にそのまま載せる。
直した方が良いことが明確な指摘（直す内容が指摘から一つに決まり、受け入れ条件と設計の判断を変えないもの）には、直した後の文面か差分の案を添えて、承認を求める。
それ以外の指摘は、直すかどうかを人間に尋ねる。
承認された直しは、レビューを受けた commit を書き換えず、元の作業を終えてから別の作業として行い、レビューを通す。

commit を伴う作業で完了と言ってよいのは、次の検査が終了コード 0 を返すときだけである。

```
${CLAUDE_PLUGIN_ROOT}/tools/records/verdict check --task <作業ID>
```

終了コードが 0 以外なら、次のように扱う。

- 1（不合格）：指摘に対応して commit し、レビューを依頼し直す。
- 2（状態不明）：止まり、出力をそのまま報告する。
- 3（未レビュー）：レビューを省かずに止まり、未レビューであることとその理由を報告する。commit がレビュー結果の後に変わった場合もこれに当たる。
- 4（確認できず）：成果を直さず、出力が示す足りない材料を足して、レビューを依頼し直す。材料を足せないとき、または `review` が確認できずが続いたとして止まったときは、止まって人間に報告する。
