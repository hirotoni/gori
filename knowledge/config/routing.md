依頼を受けたら、作業に入る前に手順書を選ぶ。
索引（`${CLAUDE_PLUGIN_ROOT}/knowledge/index.md`）は、この指示の後ろに注入してある。
索引の手順書の行は、参照キー、適用場面、パスの三列から成る。
判断基準の行は、参照キー、適用場面、規則、パスの四列から成る。
依頼に当てはまる手順書を一つ選び、その行のパスを Read で読む。

読んだら、slug を決めて記録を始める。作業 ID は道具が着手の時刻を付けて発行する。
チケットから始める作業は、slug をチケット番号から始める（例：slug `proj-123-login-timeout`、作業 ID `20261108-103015-proj-123-login-timeout`）。worktree、ブランチ、記録の名前からチケットを引けるようにするためである。

```
${CLAUDE_PLUGIN_ROOT}/tools/records/log start --slug <slug> --what "<目的>" --procedure procedures/<id>
```

出力の最終行の `TASK_ID=` の値を、以後の作業 ID に使う。
道具が手順書の手順を、判断の記録に一字一句写す。
以後、手順を終えるたびに step-done を書き、飛ばす手順には理由を付けて step-skip を書く。
書き方は `skills/decision-log` に従う。

当てはまる手順書が無ければ、その場で手順書を書いてから始める。
見出しは「## 対象」「## 手順」「## 禁止事項」「## 終わりの条件」「## 報告」の五つにし、手順は 1. から始まる番号付きリストにする。
手順書はファイルに置かず、`--procedure -` を渡して標準入力で `log start` に渡す。
手順は start のときに判断の記録へ写されるので、それより後に手順書は要らない。

```
${CLAUDE_PLUGIN_ROOT}/tools/records/log start --slug <slug> --what "<目的>" --procedure - <<'PROCEDURE'
## 対象
...
PROCEDURE
```

計画に沿った開発や、人間からの依頼は、手順書で進める。
プールに起票するのは、抽出が見つけた学び、`skills/procedure-scout` が見つけた手順書の候補、作業の中で見つけた不具合や改善の候補に限る。
計画の作業をプールに載せると、担当が人間に設計の判断を確かめられないまま進め、学びの件数とも混ざるためである。
起票先は、直すファイルのあるリポジトリのプールである。gori の道具や知識ファイルの不備は、どのリポジトリで見つけても gori のプールに起票する（`skills/improvement-add`）。

次の小さな依頼に限り、振り分けを省いて直接処理してよい。

- 変更を伴わず、一度か二度の読み取りで答えられる質問。コードを調べて根拠を示す必要がある問いは、振り分けを通す。
- 一つのファイルの数行の修正で、確かめ方が明らかなもの。

省いた場合も、確かめずに完了と言わない。

次は、振り分けを通すかどうかに依らず、どの作業でも守る。
索引の判断基準の行の規則は、本体を読んでいなくても守る。本体は、その規則を使うとき、または境目で迷ったときに読む。
手順書と判断基準が食い違っていたら、判断基準に従い、食い違いを報告に載せる。
人間の指摘が、その場限りでなく、場面をまたぐ規則の形をしていたら、作業の報告で、判断基準に足すかを一行尋ねる。プールには起票しない。
設定の値や実装の振る舞いを文書に書くとき、または人間に伝えるときは、その設定や実装を読んで確かめてから書く。
確かめていない点は、確かめていないと明記する。
依頼や指摘が何を指すのか（成果物、用途、対象、名前か中身か）が文面から一つに決まらないときは、案や計画を作る前に人間に確かめる。
これは人間だけが答えを持つ問いであり、推測で一つに決めて進めない。
人間に問いを出したら、返事を読むたびに、問いごとに答えがあったかを分ける。
答えがあった問いだけを決まったものとして扱い、答えの無い問いと、案を進めることの承認は、決まっていないものとして残す。
案を変える指示は、その点への答えであり、案全体の承認ではない。
問いが残っていれば、決まったことを短く確かめたうえで、残った問いだけを尋ね直す。すべての問いが決まり、承認がはっきりするまで、変更を始めない。
人間の返事に、中身まで承認された作業と、答えを待つ問いが一緒にあれば、作業は `skills/delegate` で委任するか、バックグラウンドの命令で始め、同じ返答で問いに答えてターンを終える。
長いテストやレビューも、前景で待たない。委任した作業の結果は、通知を受けてから報告する。
委任するのは、中身まで承認された作業に限る。委任先は人間に尋ねられないためである。並行する作業は、別の作業 ID と worktree で進める。
他のリポジトリで、gori のもの（プール、記録、道具）を指す名前を付けるときは、名前に gori か GORI_ を入れる。
人間への返答は、指示が無い限り、会話を始めたときの言語で書く。
道具、サブエージェント、レビュアーの出力が別の言語でも、それに合わせない。

人間への報告で gori 自身の仕組みに触れるかは、索引の後ろに注入した `GORI_SYSTEM_REPORT` の値で決める。
1 なら、仕組みの事情も報告に書いてよい。
0 なら、gori の仕組みの説明（判断の記録やレビュー結果の置き場所、lint、索引の作り直し、レビューの手続きの経過、記録の書き方の事情）を報告に書かない。記録はこれまでどおり書く。
0 でも、gori 自身を変える作業の中身、レビューの不合格や検査の失敗や片付け残しのように人間の対応が要ること、尋ねられたことは報告する。
