# 自己改善ハーネスの要件

この文書は、エージェントに仕事を任せるための自己改善ハーネスについて、満たすべき要件を定義する。
各要件には、それが防ぐ失敗を添える。
要件は仕組みの水準で書き、実現の手段は問わない。
手段の例を挙げる場合も、一つの解として示す。

## 1. ハーネスが解く問題

エージェントに仕事を任せると、次の三種類の失敗が起きる。

- **手順の失敗**：同じ種類の仕事でも毎回違う進め方をし、検証や比較を飛ばす。
- **レビューの失敗**：検証していないことを「できた」と報告し、それが信用される。
- **学習の失敗**：人間が同じ指摘を何度もしても、次のセッションのエージェントは覚えていない。

ハーネスは、エージェントの外側に置く知識と仕組みによって、この三つを減らすものである。
前の二つは一回の作業の中で、三つ目は作業をまたいで効く。
そこで、ハーネスを二つのループとして捉える。

- **実行ループ**：依頼を受けて、手順に従い、検証し、成果を渡す。一回の作業の中で回る。
- **改善ループ**：実行ループの記録から学びを取り出し、ハーネス自身を書き換える。作業をまたいで回る。

改善ループが書き換える対象は、実行ループが読む知識と仕組みである。
したがって、知識と仕組みは、改善ループが安全に書き換えられる形で持っておかなければならない。
以下の要件は、この構造に沿って並べた。

## 2. 知識の表現

### H-K1 知識を種類ごとに分けて持つ

エージェントに渡す知識を、次の五種類に分けて別々の単位で持つ。

| 種類         | 答える問い                         |
| ------------ | ---------------------------------- |
| **手順**     | この種類の仕事を、どの順で進めるか |
| **能力**     | ある部分作業を、どうやって行うか   |
| **判断基準** | 迷ったとき、何を優先するか         |
| **役割**     | 委任先は誰で、何をしてよいか       |
| **設定**     | どのモデルを、どの強さで使うか     |

防ぐ失敗：手順と判断基準が一つの文書に混ざると、ある手順だけに効かせたい修正が、他の手順の判断まで変えてしまう。
分けておけば、改善ループは影響範囲を一つの単位に限って書き換えられる。

### H-K2 業務を手順の形に落とす

繰り返し現れる仕事の種類ごとに、手順書を一つ用意する。
手順書は、対象（どんな依頼に使うか）、順序のある手順、禁止事項、終わりの条件、報告に含めるものを持つ。

防ぐ失敗：手順書が無いと、進め方の良し悪しを比べる基準が無く、改善ループが何を直せばよいか分からない。
手順書は、実行の基準であると同時に、改善の対象を特定するための座標になる。

### H-K3 判断基準は、適用する場面とともに持つ

判断基準は「何をすべきか」だけでなく「いつ適用するか」を持つ。
常に読み込むのは判断基準の一覧と、適用場面と、規則の一行だけにし、エージェントは規則を使うときに本文を読む。

防ぐ失敗：すべての判断基準を常に文脈に載せると、文脈が埋まり、どれも効かなくなる。

### H-K4 知識は参照で組み合わせ、書き写さない

ある単位が別の単位の内容を使うときは、場所を示して参照し、本文を書き写さない。

防ぐ失敗：書き写した内容は、元が直されたときに古いまま残る。改善ループが一か所を直しても、写しの側で古い規則が生き続ける。

### H-K5 知識を利用者ごとに上書きできる

ハーネスの既定を変えずに、利用者やリポジトリが自分用の差分を足せるようにする。
差分は、既定のどこを変えるかを明示した形で書く（既定の手順書の文言を引用して位置を指定する、など）。
既定が更新されて差分の位置が見つからなくなったら、黙って当てはめず、検出して報告する。

防ぐ失敗：既定を直接書き換えると、既定の更新を取り込めなくなる。位置の分からない差分を推測で当てはめると、意図しない手順に効く。

## 3. 実行ループ

### H-E1 入口で振り分けを強制する

すべての依頼が、まず振り分けを通るようにする。
振り分けは、依頼を手順書の一つに対応づけ、手順書が無ければ、その場で手順書を設計する経路に回す。
小さな依頼は、振り分けを省いて直接処理してよい。その境界も明示する。
振り分けの指示は、エージェントの記憶に頼らず、セッションの開始時に毎回文脈へ入れる。

防ぐ失敗：振り分けを任意にすると、エージェントは手順書を読まずに始める。

### H-E2 手順を写して、逸脱を見えるようにする

作業を始めるとき、選んだ手順書の手順を一字一句写した作業リストを作る。
実行しない手順も消さず、理由を添えて残す。

防ぐ失敗：手順を記憶だけで追うと、飛ばしたことに本人も気付かない。
写しがあれば、飛ばした手順とその理由が記録に残り、改善ループが「この手順は毎回飛ばされている」と検出できる。

### H-E3 状況に応じた能力の呼び出しを、規則として持つ

「この状況では、この能力を必ず使う」という対応表を持つ（関数の境界をまたぐコードなら設計の比較、コミットの前なら清掃、など）。

防ぐ失敗：能力の使用をエージェントの裁量に任せると、使うべき場面で使わない。

### H-E4 自律の境界を、可逆性で引く

エージェントが確認なしに進めてよい範囲と、必ず止まる範囲を、操作が取り消せるかどうかで分ける。
取り消せる操作は進め、結果を見せて人間に修正させる。
取り消せない操作（共有ブランチの書き換え、デプロイ、データ削除、外部への送信）の前では止まる。
観察すれば答えが分かる問いは、人間に尋ねずに試して決める。

防ぐ失敗：境界が曖昧だと、エージェントは可逆な判断で人間を待たせるか、不可逆な操作を勝手に行うかのどちらかに偏る。

### H-E5 完了のレビューを、作業者から切り離す

完了と認めるのは、実物（動いているシステム、実際の出力）で確かめたときに限る。
重要なレビューは、その成果を作っていない者が下す。
レビューは、レビューした対象の版（コミットの識別子など）に結びつけ、対象が変われば無効にする。
レビューできる者がいないときは、レビューを省かずに未レビューとして止める。

防ぐ失敗：作業者が自分の成果をレビューすると、自己申告がそのまま完了になる。
レビューを版に結びつけないと、レビュー後に入った変更が、レビュー済みとして通ってしまう。

### H-E6 委任には契約を持たせる

作業をサブエージェントに委任するとき、依頼文に、目的、範囲、受け入れ基準、検証方法、禁止事項、報告の形式を含める。
委任先の成果は、委任元が自分で読み、自分の言葉でまとめる。
新しい仕事には新しい委任先を立て、前の委任先の会話を引き継がない。

防ぐ失敗：曖昧な依頼文は、曖昧な成果を生む。会話を引き継いだ委任では、途中の指示が抜け落ちやすい。

### H-E7 多様性はモデルの違いから得る

複数の視点が必要な作業（レビュー、設計の競作、審査）では、同じモデルに別の人格を演じさせるのではなく、異なるモデルを使う。
複数のモデルが独立に同じ結論に達したことを、強い証拠として扱う。

防ぐ失敗：同じモデルは同じ盲点を持つため、人格を変えても同じ見落としが重なる。

### H-E8 書き手を一つに絞る

同じ対象（ファイル、ブランチ、作業場所、共有の状態）に書き込む者を一人に限る。
並列に動く委任先には、それぞれ専用の作業場所を与える。

防ぐ失敗：書き手が複数いると、互いの変更を上書きし、どの変更が検証済みか分からなくなる。

### H-E9 状態をエージェントの外に置く

長い作業の状態（進捗、判断、レビュー結果、中断点）を、会話の文脈ではなくファイルに置く。
中断するときは再開に必要な情報を書き出し、再開するときはまずそれを読む。

防ぐ失敗：文脈は圧縮や再起動で失われる。状態が文脈にしか無いと、再開したエージェントは済んだ作業をやり直すか、済んでいない作業を済んだと思い込む。

### H-E10 文章で守れない規則は、道具で守る

規則のうち、守られなかったときの被害が大きく、機械的に判定できるものは、スクリプトや検査で強制する。
その道具は、状態が不明なときに危険な操作を許さない側へ倒す。
対象の例は、PR が準備完了かの判定、マージやブランチの書き換えの前の確認、共有状態への書き込みの排他、計画書の形式の検査である。

防ぐ失敗：被害の大きい規則を文章だけで守らせると、一度の見落としが取り返せない結果になる。

### H-E11 承認済みの作業を、人間の指示を待たずに始める

人間が着手を承認した作業は、人間がセッションを開いて指示しなくても始まるようにする。
受け入れ条件の承認は着手の承認と一度に済ませ、作業が途中で承認を待って止まらないようにする。
無人で進めるのは、作業者から切り離したレビュー（H-E5）に合格するところまでとする。
取り消せない操作（共有ブランチへの取り込み、外部への送信）は、人間の指示を待つ。
例外として、ハーネス自身の誤りから抽出した学びの適用に限り、合格した成果を無人で手元の共有ブランチに取り込んでよい。取り込むのは作業者でなく道具とし、取り込んだことは人間に知らせず、実行の記録に残す。外部への送信は、この場合も人間の指示を待つ。
無人の作業には、人間の決定に当たる操作（着手の承認、承認の記録、共有ブランチへの取り込み、外部への送信）を道具で拒ませる（H-E10）。
無人の作業の費用には、上限を重ねて置く。
ハーネスの外にある上限（契約やアカウントの設定）を一つは持ち、ハーネスの不具合があっても超えないようにする。
ハーネスの中では、一回の実行と一定期間の実行の量に上限を置き、上限の値を読めないときは起動しない。
結果の知らせ、止まった作業の再開、取り込みの指示は、決まった一つの窓口に集める。

防ぐ失敗：着手を人間の指示に頼ると、承認済みの作業が、人間の手が空くまで始まらない。
途中の承認で止まる作業は、人間が気付くまで放置される。
無人の作業が人間の決定に当たる操作をできると、自分の作業を自分で承認して取り込める。
費用の上限がハーネスの中にしか無いと、ハーネスの不具合で上限が効かず、意図しない請求が生じる。

## 4. 改善ループ

改善ループは、観察、抽出、選別、承認、適用、検証、刈り込みの七段から成る。
ループ自体が回っているか、回して良くなったかも、ハーネスが自分で確かめる（H-I10 から H-I13）。

```txt
 実行ループの記録 ──► 抽出 ──► 選別 ──► 承認 ──► 適用 ──► 検証 ──┐
   (会話の記録,                                                    │
    判断の記録,                                                    │
    使用の記録)  ◄─────────────── 次の実行 ◄──────────────────────┘
                                   ▲
                       刈り込み ───┘
```

### H-I1 実行の記録を、後から読める形で残す

改善の材料として、少なくとも次の三つを残す。

- **会話の全記録**：何を指示され、何をし、何を訂正されたか。
- **判断の記録**：判断ごとに、何を決めたか、なぜか、証拠は何か、結果はどうなったかを一行ずつ。追記だけにし、訂正は新しい行で行う。
- **使用の記録**：どの手順書や能力が、どれだけ使われたか。

防ぐ失敗：記録が無いと、改善は人間の記憶に頼るしかなくなる。判断の記録が文章だけだと、主張と証拠を突き合わせられない。

### H-I2 記録から学びを抽出する仕組みを持つ

会話の記録を読み、繰り返し使える学びを取り出す専用の手順を持つ。
抽出は、異なる観点（判断の誤り、道具の不足、別の進め方の可能性）を持つ複数の読み手に並列で行わせ、まとめ役が引用を確かめて統合する。
一度しか起きていないことは学びとして扱わない。
会話の外から来る指摘（レビューボットの指摘、人間のレビュー）からも、同じ型の指摘を学びとして蓄える。

防ぐ失敗：一人の読み手は、自分が気付ける種類の問題しか拾わない。一度きりの出来事を規則にすると、規則が増えるだけで効かなくなる。

### H-I3 学びを、最も強い形で定着させる

学びをハーネスに入れるときは、強制力の強い形から順に検討する。

1. **構造**：誤りが起きえない設計にする（状態の持ち主を一つにする、古い道を消す）。
2. **型と検査**：誤りを書けないようにするか、書いたら検査が失敗し、その失敗が直し方を示すようにする。
3. **テスト**：振る舞いが壊れたら失敗するテストを足す。
4. **文章**：判断が必要で、上の三つで表せないものだけを、手順書や判断基準に書く。

同じ指示を二度書きそうになったら、それは文章では守られていない証拠であり、上の段へ移す。
新しく足した検査は、過去に実際に起きた誤りで失敗することを示す。

防ぐ失敗：学びをすべて文章で足すと、手順書が膨らみ、どの規則も読まれなくなる。文章の規則は、守られなかったときに何も失敗しない。

### H-I4 ハーネスの変更には人間の承認を挟む

抽出した学びのうち、ハーネスの知識を書き換えるものは、人間の明示的な承認を得てから適用する。
承認は二か所に置く。
着手の前に、何が満たされれば完了かを人間が承認する。
ハーネスに取り込む前に、レビューに合格した変更を人間が承認する。
この二つの間は、人間の承認を待たずに進めてよい。
すぐに直さないものは、承認待ちの課題として起票し、失わない。

防ぐ失敗：ハーネスの変更は、以後のすべての作業に効く。エージェントが誤った学びを自動で適用すると、誤りが全作業に広がる。

### H-I5 ハーネスの変更自体を、手順に従って行う

手順書や能力の追加と修正にも、専用の手順を持つ。
その手順は、形式の検証（必須の項目、参照先の存在、他の単位へのリンクの解決）と、迷ったら削る方針を含む。
変更の規模が大きいものは、作成、試験、改善を繰り返す別の手順に回す。

防ぐ失敗：ハーネスの変更だけ手順の外で行うと、改善ループがハーネスを壊す経路になる。

### H-I6 変更の効果を、盲検で評価する

手順書や判断基準の変更が、エージェントの振る舞いを実際に良くするかを試す手順を持つ。

- 候補のエージェントには、評価されていることを知らせない。
- 採点基準は採点者だけが持つ。
- 採点者は、どの候補がどの変更によるものかを知らない状態で採点する。可能なら作業者と別系統のモデルを使う。
- 手順に従ったかは、自己申告ではなく、実際に開いたファイルなどの記録から判定する。

防ぐ失敗：評価を知った候補は、評価向けに振る舞う。変更の作者が採点すると、変更を良く見せる方向に偏る。

### H-I7 検証の仕組み自体を保守する

実行ループが使う検証の仕組み（アプリを操作する手順、形式検証のモデル）は、製品の変化に合わせて古くなる。
これを定期的に製品の現状と突き合わせ、ずれを直す手順を持つ。
その手順は、検証の仕組みだけを書き換え、製品のコードは直さない。
ずれが製品の不具合によるものなら、直さずに報告する。

防ぐ失敗：古くなった検証の仕組みは、壊れた製品を合格させる。保守の手順が製品を直し始めると、検証が検証対象に合わせて曲がる。

### H-I8 使われないものを刈り込む

手順書と能力の使用回数を定期的に集め、使われていないものを削除の候補にする。
迷ったら削る。

防ぐ失敗：改善ループは知識を足す方向に偏りやすい。足すだけのハーネスは、振り分けの選択肢と文脈の消費が増え続ける。

### H-I9 外部からの更新と、手元の改善を両立させる

ハーネスの既定を外部から取り込む場合、手元の差分が取り込みで壊れていないかを検出する。
取り込まない方針を取るなら、取り込んだ後に、外したはずの部分が戻っていないかを検査する。

防ぐ失敗：取り込みのたびに手元の改善が黙って失われると、改善ループの成果が積み上がらない。

### H-I10 抽出を、人間の呼び出しに頼らず起動する

学びの抽出を、作業の終わりや一定期間ごとに自動で始める。
人間が呼び出すことでも始められるようにする。
自動で始めるのは抽出と起票までとし、ハーネスへの適用は H-I4 の承認を待つ。

防ぐ失敗：抽出が人間の呼び出しでしか始まらないと、忙しいときほど学びが取りこぼされ、改善ループが止まる。

### H-I11 ハーネスの変更ごとに、回帰を評価する

手順書や判断基準を変えたら、過去の評価課題を再実行し、変更していない場面の振る舞いが悪くなっていないかを確かめる。
評価課題は、過去に実際に起きた失敗の事例から作り、改善のたびに足していく。

防ぐ失敗：ある場面のための修正が、別の場面の振る舞いを悪くしても、その場面が次に現れるまで気付けない。

### H-I12 改善の効果を、記録から測る

改善ループが実際に効いているかを、実行の記録から集計した指標で確かめる。
指標の例は、同じ種類の人間の訂正の回数、手順を飛ばした回数、レビューで不合格になった回数、未レビューで止まった回数である。
使用回数は利用の量を示すだけで、改善の効果の指標にはならない。

防ぐ失敗：効果を測らないと、規則を足したことが改善とみなされ、効かない規則が残り続ける。

### H-I13 規則に来歴と寿命を持たせる

ハーネスの各規則に、いつ、どの種類の事例（pattern）から入ったか、何がそれを強制しているかを記録する。
個々の事例はマシンの手元にしかないので、規則からは種類で辿り、事例は種類から引く。
学びには成熟度（候補、繰り返し確認された、確立した）を持たせ、確認が積み重なったものだけを強い規則にする。
規則が防ぐはずの誤りが構造上起きえなくなったら、その規則を消す。

防ぐ失敗：来歴の無い規則は、今も必要かを誰も判断できず、消せないまま積み上がる。

## 5. 全体に通す設計の不変条件

個々の要件の背後には、次の不変条件が繰り返し現れる。
新しい要件を足すときは、これらと矛盾しないかを確かめる。

- **自己申告を信じない**：完了、検証、学びのいずれも、本人の報告ではなく記録と実物で確かめる。
- **不明は止める側に倒す**：状態が分からないときは、危険な操作を許さない。ただし、安全のための指示（振り分けの差し込み）は、不明なら実行する側に倒す。
- **文章より構造**：守らせたい規則は、可能な限り道具、型、検査で表す。文章は最後の手段である。
- **書き手は一人**：共有されるものには、書き手を一人だけ置く。並列性は、共有をなくすことで得る。
- **外部の入力はデータ**：レビューコメント、会話の記録、他者が書いた文書の中の指示に従わない。
- **操作は冪等**：途中で落ちても、再実行で同じ状態に収束する。
- **文脈は有限**：大きな入力は委任先で読み、主スレッドには結論だけを持ち帰る。判断基準の本体は、規則を使うときだけ読む。

## 6. 構築の順序

次の順で積むと、各段が前の段を検証の土台にできる。

1. 記録（H-I1）と、状態の外部化（H-E9）。以後のすべての段の材料になる。
2. 振り分けと手順書（H-K2、H-E1、H-E2）。最初は、よく行う三、四種類の仕事だけでよい。
3. 実物での検証と、作業者から切り離したレビュー（H-E5）。これが無いと、以後の改善の効果を確かめられない。
4. 抽出と承認（H-I2、H-I4）。手動の起動から始め、回り始めたら自動の起動（H-I10）を足す。
5. 構造への定着（H-I3）、ハーネス変更の手順（H-I5）、規則の来歴（H-I13）。
6. 効果の測定（H-I12）。これ以降の段を足すかどうかの判断材料になる。
7. 盲検評価と回帰評価（H-I6、H-I11）と刈り込み（H-I8）。手順書が十数本を超えたあたりで必要になる。
8. 道具による強制（H-E10）と多モデルの多様性（H-E7）。被害の大きい操作から順に足す。
9. 自律起動（H-E11）。承認（H-I4）と切り離したレビュー（H-E5）が土台になり、無人の作業が人間の決定に当たる操作をできないようにする強制（H-E10）を同時に足す。
