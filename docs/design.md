# gori の設計（メンテナ向け）

この文書は、`harness-requirements.md` の要件を満たす gori の仕組みと、そう決めた理由を示す。
読み手は、gori を直すメンテナと、その変更のレビュアーである。
gori を使う人は README を読めばよい。二つのループと上流の概念図も README にある。
要件の番号（H-K1 など）は `harness-requirements.md` の番号を指す。
道具の細部は各道具のファイルと各知識ファイルが正であり、この文書は要点と置き場所だけを示す。

## 1. 前提

- gori は独立したマーケットプレイス兼プラグインとして、このリポジトリに置く。
- 知識ファイルの文章は日本語で書く。
- 複数のモデルを使う場面では、Claude のモデル（fable、opus、sonnet、haiku）だけを使う。
- このリポジトリは、ハーネスの利用を始めるときのベースラインである。
  どのマシンも、このリポジトリを clone して `tools/repo/install` で導入し、そのチェックアウトを独自に育てる。
  公開リポジトリを育てる上流のマシンは一台で、ほかのマシンは自分の改善を上流に戻さない（3 章「公開と上流」）。
  そのため、各マシンの gori は、使うほど別々の方向へ進化する。
  clone と install の入れ方だけを支えるので、gori が動くマシンには必ず gori のチェックアウトがある。
- 学び（事例と抽出待ちの会話）、改善候補のプール、作業の記録は、どのマシンでも git の管理外に置き、gori のチェックアウトの git の共通ディレクトリ（`git rev-parse --git-common-dir`）の下の `gori/` に手元だけで持つ。
  作業ツリーの外なので、exclude は要らない。
  ベースラインに入るのは、学びを適用した知識ファイルの変更だけであり、各マシンの学びもその形でベースラインになる。
  そのため、知識ファイルの来歴は事例の id を持たず、誤りの種類の名前（`pattern`）だけを持つ（2 章「事例と来歴」）。

## 2. データの形

### 知識ファイル

五種類の知識ファイルを、Claude Code が読み込める場所に種類ごとに分けて置く（H-K1）。

| 種類     | 置き場所                         | 読まれ方                                 |
| -------- | -------------------------------- | ---------------------------------------- |
| 手順     | `knowledge/procedures/<id>.md`   | 振り分けが選んだときにパスで読む         |
| 判断基準 | `knowledge/criteria/<id>.md`     | 規則の一行は索引で毎回文脈に入る。本体は、規則を使うときにパスで読む |
| 能力     | `knowledge/skills/<id>/SKILL.md` | Skill ツールで呼ぶ                       |
| 役割     | `knowledge/agents/<id>.md`       | Agent ツールの委任先として使う           |
| 設定     | `knowledge/config/<id>.md`       | 振り分け、対応表、モデルの表として読む   |

どの知識ファイルも、次の frontmatter を持つ（能力は `name` と `description` も持つ）。

```yaml
id: bug-fix
kind: procedure # procedure | criterion | capability | role | config
when: 報告された不具合（期待と違う振る舞い、エラー）の原因を突き止めて直すとき
refs: [skills/decision-log, criteria/autonomy, criteria/done]
provenance:
  added: 2026-11-08
  source: harness-requirements.md H-K2, H-E5
  patterns: []
  enforced_by: [lint:procedure-sections, lint:procedure-steps, verdict:check]
```

手順書の本文は、対象、手順、禁止事項、終わりの条件、報告の五つの見出しを持ち、手順は 1. から始まる番号付きリストにする（H-K2）。
`enforced_by` は、その規則を強制している検査の名前を指し、文章だけで守っている規則は `[]` になる（H-I13）。
検査の名前は `lint:<tools/knowledge/lint の rule-id>`、`test:<tests/ の下のテストファイルの名前>`、`verdict:<tools/records/verdict の検査>`、`log:<tools/records/log の検査>` の形で書き、`tools/knowledge/lint` が実在を確かめる（`unknown-enforcer`）。
`tools/knowledge/lint` は、ほかに frontmatter、置き場所、参照、手順書の見出しと手順、名指し、書き写しを検査し、壊した知識ファイルの例は `tests/knowledge/fixtures/` にある（H-K4、H-I5）。

### 事例と来歴

**事例**：規則の根拠になった一回の出来事を gori の形で記録したもので、`gori/learning/cases/<id>.md` に一ファイルで置く。

```yaml
id: 2026-01-04-judge-sandbox-unverifiable
type: verdict-fail # correction | skipped-step | verdict-fail | verdict-unverified | blocked
pattern: judge-sandbox-unverifiable # 同じ種類の出来事に共通の名前
verdict: <sha>/<レビュー結果のファイル名>.json # 会話の発言から拾ったときは session と message
quote: 行 14（行 12 の訂正）を確かめきれない
```

本文には、何が起き、何が正しかったかを、会話の記録が消えても読めるように書く。
事例を書くのは `tools/learning/case` だけで、書く時点で引用を会話の記録かレビュー結果の findings と照合し、秘密情報らしい文字列を拒み、既存の id を上書きしない。
事例の `quote` が会話の記録に含まれるかを `tools/knowledge/lint` で重ねて確かめることはしない。書く時点で照合しているためである。
抽出は、同じ `pattern` の事例が二件以上になったものだけを学びにする。人間が `todo` に上げた学びは件数に依らず適用する。
誤って書かれた事例は書き換えず、`case retract` で `gori/learning/retractions/<id>.md` に理由を一度だけ書いて取り消す。
取り消した事例は件数に数えない。同じ発言を同じ `pattern` で書き直すことも、重複の検査が止める。

参照の向きは、知識ファイルから pattern へ、プールの学びの一件から事例へ、の二つだけにする（知識ファイルも検査もプールを参照しない）。
知識ファイルの `provenance` が改善候補のプールの一件（`pool:<ID>` や `<YYYYMMDD>-<hhmmss>-<slug>` の形）を指せば、手元のプールの有無に依らず `tools/knowledge/lint` が落とす（`pool-provenance`）。プールは手元にしかなく、別のマシンでは指す先が無いためである。

学びを適用したら、その `pattern` を `provenance.patterns` に足す。
新しく作る知識ファイルなら `source` に「学び: <pattern>」と書き、既存の知識ファイルなら `source` を変えない。
要件から直接入れた規則は、`source` に要件の番号を書き、`patterns: []` にする。
事例の id は来歴に書かない。
事例はマシンの手元にしかないので、id を書くと、自分の事例を持つ別のマシンで指す先が無くなるためである。
pattern の名前は、どのマシンでも同じ種類の誤りを指す。

知識ファイルに成熟度の欄は持たせない（H-I13 のうち成熟度は見送った）。値で振る舞いを変える仕組みが無く、事例を数えて書く手間だけが残ったためである。
規則の強さは、`enforced_by` が検査を指すかで読む。
`tools/knowledge/lint` は、`patterns` の各要素が pattern の形であることと、`provenance.cases` が書かれていないこと（`bad-value`）を確かめる。
`provenance.cases` を見つけたときは、手元の事例から各 id の pattern を引いて置き換えた後の `patterns` の行を示し、手元に無い id と取り消した id を名指しする。上流から欲しいところだけを取り込んで古い形の知識ファイルが残ったマシンが、そのまま置き換えられるようにするためで、事例を読むのはこの出力のためだけである。

`provenance.cases`（事例の id の一覧）を使っていた知識ファイルは、形だけをこの形に移す。
`cases: []` を消して `patterns` を置き、`source` が「学び: <pattern>」のものはその pattern を `patterns` に写し、残りは `patterns: []` にする。
それより前に既存の知識ファイルへ足した学びの pattern は、記録からさかのぼって埋めない。
どの知識ファイルにどの pattern が入ったかを一件ずつ照らすと取り違えが起きうるうえ、以後の適用で `patterns` は足されていくためである。

### 索引と入口

`knowledge/index.md` は `tools/knowledge/build-index` が frontmatter から生成し、手で書かない（`tests/run.sh` が `--check` で食い違いを落とす）。
手順書の行は、参照キー、`when`、読み込めるパスの三列である。判断基準の行は、`when` の次に `rule` を持つ四列である（H-K3）。
SessionStart フック（`tools/hooks/session-start`）が、振り分けの指示（`config/routing`）と索引を毎回注入する（H-E1）。
続けて、全リポジトリのプールに proposed の候補があればその件数を、実際に走った最新の抽出が 0 以外で終わっていればそのことを、一行ずつ足し、最初の返答で人間に伝えさせる（H-I4、H-I10）。無人の作業、抽出、レビューのセッションでは足さない。
状況ごとに必ず使う能力と判断基準は `config/triggers` の表にある（H-E3）。
手順書が無い依頼は、その場で手順書を書き、`log start --procedure -` に標準入力で渡して始める（`config/routing`）。
知識ファイルの編集の後のフォーマッタは、`.prettierignore` で `knowledge/` を外し、知識ファイルの形を崩させない。

### 判断基準の規則

判断基準は、規則を一行で frontmatter の `rule` に持ち、索引がその行を毎回文脈に入れる。
解く問題は、人間が当たり前と考える経験則が、担当の文脈に入らないまま作業が進み、人間が同じ指摘を繰り返すことである。
索引の行が適用場面しか持たないと、担当がその場面だと気づいて本体を読むまで、規則は文脈に入らない。
迷っていない担当には、読みに行く形の規則は届かない。

原則という別の種類は作らない。
判断の規則の置き場所が二つになり、どちらに書くかの判断が増えるためである。
設定のファイルに規則を一行ずつ並べる案も、同じ理由で採らなかった。
本体の要らない規則は、短い判断基準として足す。

索引の判断基準の行は、参照キー、`when`、`rule`、パスの四列にする。
本体は、その規則を使うときに読む。
本体ごと注入する案は、数が増えると一つひとつが埋もれるので採らなかった。

`rule` は一文か二文で、一行に書く。
一文目は、することを言い切る。
二文目は置くなら、やりがちな誤りの名指し、境目の条件、守れたかの見分け方のどれかにする。
規則を守ったつもりで外れる先を、先に塞ぐためである。
理由は `rule` に入れず、本体に最低一文書く。境目の場面で担当が判断する材料になる。
`tools/knowledge/lint` は、`rule` があることと一行であることだけを確かめる。
`rule` が無いときは、本体の冒頭の一文から作った `rule:` の行を示す。`rule` を持つ前の判断基準は、規則を本体の冒頭の一文に書いていたので、上流から欲しいところだけを取り込んだマシンが、その行を起点に置き換えられる。候補は一文目だけなので、規則が二文に及ぶなら、二文目は手で足す。
新しく足す判断基準の id は、場面ではなく規則を表す名前にする。
人間が名前で指示するときに、名前から規則を思い出せるためである。
元からある五件（`criteria/autonomy`、`criteria/design-scope`、`criteria/done`、`criteria/harness-shape`、`criteria/user-environment`）の id は、場面を表す名前のまま変えない。

足してよいのは、人間が当たり前として述べた、場面をまたぐ規則である。
人間が述べたものなので、二回起きるのを待たず、一件で足す。
担当は候補をプールに起票しない。人間の指摘が一般の規則の形をしていたら、作業の報告で、足すかを一行尋ねる。
担当が候補を積むと、数が増えて一つひとつが効かなくなるためである。
足す前に、既にある規則に畳めないかと、検査や道具で守らせられないかを確かめる。
学びの適用から判断基準に入る道（`skills/encode`）は変えない。
件数の上限は決めない。索引に全件が並ぶので、多すぎるかは人間が見て判断する。

規則は判断基準にだけ書き、手順書、能力、役割、文書は言い直さずに参照キーで指す。
作業の途中で手順書と判断基準が食い違っていたら、担当は判断基準に従い、食い違いを報告に載せる。
判断基準を足すか変えるときは、食い違う箇所をリポジトリ全体から洗い出し、直し方を一度の承認で示して、一つの作業、一回のレビューで直す。
そのために、`procedures/harness-change` の、知識ファイルごとに作業を分ける決まりに例外を足す。
知識ファイルごとに分けると、一つの規則の変更が複数の作業とレビューに分かれ、その間、食い違ったままの状態が main に入るためである。

判断基準が選択を変えたら、担当は判断の記録の decision 行の理由に、その参照キーを書く。
守られなかった規則はレビューと抽出が拾うので、足すのは守られた側の跡だけである。行の種類も道具も足さない。
返答のたびに使った規則を述べさせる案は、報告に仕組みの事情を書かない設定（`config/routing`）と合わないので採らなかった。

実装の役割（`agents/implementer`）の定義に、索引の判断基準の行を始めに読むと一文足す。
委任元が当てはまる規則を選んで依頼文に写す案は、委任元が気づかなかった規則が届かないので採らなかった。
委任先が始めに索引を読むことは、`tests/e2e/implementer-reads-index.sh` が確かめる。
レビュアーには届けず、判断基準への違反を不合格の条件に足さない。レビューの基準が広がるためである。

判断基準の規則には、人間が、開発で当たり前とする規則として選んだものを含む。
元からある判断基準と同じ規則は、ファイルを足さず、その `rule` に畳む。`criteria/done` と `criteria/autonomy` の二文目がこれに当たる。
ほかの知識ファイルと重なる規則は、判断基準の側が正本である。
原因の場所で直す決まりは `criteria/fix-root-cause` に、定着の順は `criteria/encode-in-structure` にあり、`procedures/bug-fix`、`criteria/harness-shape`、`skills/encode` はそれを指す。

新しい要件を、最初からあったかのように設計し直して入れる規則（`criteria/redesign-for-requirement`）は、`criteria/design-scope` と押す向きが逆になる。
前者は要件の入れ方を決め、後者は触る広さの上限を決める。
要件が触れる部分は、継ぎ足さずに設計を直す。
触れない部分まで直したくなったら、直さずに、理由を添えた選択肢として人間に示す。

この仕組みは、次の部品から成る。
上流から取り込むなら、一覧を揃えて取り込む。一部だけを取り込むと、たとえば `build-index` だけが新しく判断基準に `rule` が無いとき、索引を作れなくなる。

- `knowledge/criteria/` の各判断基準の frontmatter の `rule`：規則の一行を持つ。
- `tools/knowledge/build-index`：索引の判断基準の行に `rule` の列を足す。`rule` の無い判断基準があれば、索引を作らない。
- `knowledge/index.md`：`build-index` が生成する索引。
- `tools/knowledge/lint`：`rule` があり空でないことを確かめ、無ければ候補の行を示す。
- `tools/knowledge/show`：本体の前に `rule` を出す。
- `knowledge/config/routing.md`：索引の列の説明、規則を本体を読まずに守ること、手順書と食い違えば判断基準に従うこと、規則の形をした指摘を報告で尋ねることを持つ。
- `knowledge/agents/implementer.md`：委任先が始めに索引の判断基準の行を読む。`tests/e2e/implementer-reads-index.sh` が確かめる。
- `knowledge/criteria/harness-shape.md`：`rule` の書き方を持つ。
- `knowledge/procedures/harness-change.md` の手順 1：判断基準を変えるとき、食い違う記述を同じ作業で直す例外を持つ。
- `knowledge/skills/decision-log`：規則が選択を変えたら、decision 行の理由に参照キーを書く。
- `tests/knowledge/` の `lint.test.mjs`、`build-index.test.mjs`、`show.test.mjs`：上の道具の振る舞いを確かめる。

`tools/hooks/session-start` は索引をそのまま注入するので、この仕組みのための変更は無い。

### 記録

**記録の場所**：gori のチェックアウトの git の共通ディレクトリの下の `gori/repos/<名前>/`。
`<名前>` は作業するリポジトリの本体のチェックアウトのディレクトリ名で、worktree の中から呼んでも同じ名前になる。

```
<gori のチェックアウト>/.git/gori/
  learning/         事例、取り消し、抽出待ち（マシン全体で一つ）
  auto/             無人の作業の実行の記録（runs/）とロック（マシン全体で一つ）
  repos/<名前>/
    repo.yml        元のリポジトリのパス
    pool/           改善候補と学び
    audit/          <作業ID>.tsv
    verdicts/       <sha>/<時刻>-<レビュアー>.json
    reviews/        E2E のログ
```

| 記録           | 置き場所                                               | 書き手                                                           |
| -------------- | ------------------------------------------------------ | ---------------------------------------------------------------- |
| 会話           | `~/.claude/projects/*.jsonl`（既定の期間で消える）     | Claude Code                                                      |
| 判断           | `repos/<名前>/audit/<作業ID>.tsv`（追記のみ）          | `tools/records/log`                                              |
| レビュー結果   | `repos/<名前>/verdicts/<sha>/<時刻>-<レビュアー>.json` | `tools/records/review` の取り込み、端末の人間の `verdict record` |
| E2E のログ     | `repos/<名前>/reviews/`                                | `tools/records/review`                                           |
| 使用           | 会話の記録から集計し、別には持たない                   | `tools/records/usage`                                            |
| 事例           | `learning/cases/<id>.md`（書き換えない）               | `tools/learning/case`                                            |
| 事例の取り消し | `learning/retractions/<id>.md`（書き換えない）         | `tools/learning/case retract`                                    |
| 抽出待ちの会話 | `learning/pending/<セッションID>`                      | SessionEnd フックが積み、`tools/learning/sessions mark` が消す   |
| 学び           | `repos/<名前>/pool/`                                   | `tools/records/pool`（`skills/improvement-add` の経路）          |

一つのリポジトリのデータが一つのディレクトリにまとまるので、片付けとバックアップが `repos/<名前>/` の単位で済み、作業のリポジトリのクローンを消しても記録が残る。
gori のデータは gori のチェックアウトが無ければ活かせないので、作業するリポジトリには置かない。
E2E のログはどの道具も読まないが、レビュー結果の根拠を後から確かめる証拠なので、レビュー結果と同じ場所に置く。
レビュアーの出力（セッションの全記録）は写さない。差分やファイルの中身を含む会話の記録で、Claude Code が既定の期間だけ残すためである。`review` は、そのセッション ID と、レビュー結果が無いときの最後の結果の文だけを端末に出す。

名前とプールの場所は、`tools/lib/pool.mjs` の一か所で決め、記録の道具（`tools/lib/audit.mjs`）も同じ決め方を使う。
最初に書くときに `repo.yml` が無ければ作り、リポジトリのパスを残す。読むだけでは作らない。
`repo.yml` のパスが今のリポジトリと食い違えば（同じ名前の別のリポジトリ、移したリポジトリ）、道具は推測で混ぜずに書かずに止まる。人間が、クローンのディレクトリ名を変えるか `repo.yml` を直して解く。
プールの道具は `--name` で名前を変えられるが、記録の道具は持たない。記録の道具は一つの作業で何度も呼ぶので、毎回渡す形にすると、渡し忘れで別の場所に書くためである。
gori のチェックアウトは道具の置き場所から決め、見つからなければ道具は書かずに止まる。

**作業 ID**：一回の作業を指す `<YYYYMMDD>-<hhmmss>-<slug>` で、`log start --slug` が着手の時刻を付けて発行する（古い形 `<YYYY-MM-DD>-<slug>` も読める）。
判断の記録のファイル名、レビュー結果の `task`、作業ブランチの名前に同じ値を使い、記録をつなぐ結合キーにする。

判断の記録は八列の TSV で、最初の start 行が手順書と作業開始時の HEAD（`base=<sha>`）を持ち、その直後に `log start --procedure` が手順を step 行として写す（H-E2）。
手順の写しを道具の側に持つので、エージェントの作業リストの形式に依らずに、手順を飛ばしたかを確かめられる。
以後は step-done、step-skip、accept（受け入れ条件）、approval（人間の承認）、check（担当の自己点検。result に点検した commit の SHA）、decision、fix、pause、resume、done の行が続き、手順が閉じていなければ done を書けず、accept 行が無ければ `review` はレビュアーを起動しない。
最後の accept 行（受け入れ条件を訂正するか取り下げる fix 行を含む）より後に approval 行が無くても、`review` はレビュアーを起動しない。人間の承認を得ないままレビューに出し、main に入れることを防ぐためである。
範囲で消したか名前を変えたファイルの名前（旧いパス、参照キー、- か _ を含むファイル名）が、行の中の印 keep-name の無い行に残っていても、`review` はレビュアーを起動しない（`tools/lib/stale-names.mjs`）。旧い名前の消し残しで不合格になり、レビューの往復が増えることを防ぐためである。
approval 行は人間の発言を引用で残し、会話の中から書くときは、`log` が引用を今の会話の最後の人間の入力と照合する。古い返事や担当の言い換えを承認として残させないためである。
承認の行は、担当が案と受け入れ条件に番号を振って示し、人間の返事から承認の言葉を切り出して書く。一つの返事が複数の問いに答えているときは、返事の全文を引く。`log add --type approval --quote <引用>` で、道具は引用が今の会話の最後の人間の入力（文章の発言、または選択式の回答の選んだ答え）に含まれることだけを確かめる。含まれなければ行を書かずに止める。返事が案を変える指示でないかと、案や受け入れ条件を左右する問いに答えているかは、担当が読み、レビュアーも確かめる。案に関わらない問いに答えが無いことでは、承認を否定しない（学び proceed-without-approval）。会話の要約の行は人間の入力に数えないので、要約の後でも、要約の前の返事を引ける。要約の行は、抽出の材料の人間の発言にも数えない。evidence は `発言 <uuid> 「<引用>」` で残す。プールの却下の照合は、これに加えて引用の外の問いでも止める。
プールの一件から始めた作業の accept 行は `pool:<ID>` だけで、`review` がレビューのたびにその一件の受け入れ条件を読む（受け入れ条件の正本をプールの一か所にする）。
書き方と `log` の使い方は `skills/decision-log` に、形の検査は `tools/lib/audit.mjs` にある。

会話の記録は機微情報を含みうるので、退避も延命もせず既定の期間で消えるに任せ、長く残すものは事例、判断の記録、レビュー結果という gori の形に要約して持つ。
会話の記録が消えても、再開、追跡、レビューは動く。
要約して持つ記録にも秘密情報を書かないよう、`log`（start と add）、`pool add`、`verdict record`、`case` は、書く欄を `tools/lib/secrets.mjs` の形で検査し、当たれば書かずに止まる。止まるときは、当たった欄と形の名前だけを出し、値は出さない。
誤って当たる文もまれにあり、そのときは伏せるか言い換えて書き直す。

### 改善候補のプール

改善候補、学び、手順書の候補は、gori 自身が持つプールに一件一ファイルで置き、`tools/records/pool` だけで読み書きする。
外の課題管理の道具に頼らないので、どのリポジトリでも、追加の CLI を入れずに改善候補を溜められる。

一件は、YAML の frontmatter を付けた Markdown のファイルである。

```
pool/20260104-153012-record-before-check.md
---
id: 20260104-153012-record-before-check
title: 判断の記録の step-done と done を、確認を済ませた後にしか書けないようにする
kind: learning                 # learning（学び）、improvement（改善候補）、procedure（手順書の候補）
status: proposed
created: 2026-01-04T15:30:12+09:00
updated: 2026-01-04T15:30:12+09:00
pattern: record-before-check   # learning だけ
cases: [2026-01-03-record-before-check]   # learning だけ
files: [tools/records/log]     # 分かっていれば
---
## 現状
## 問題
## 期待する結果
## 確認したこと
## 受け入れ条件
```

手順書の候補は、`pattern` と `cases` の代わりに、作業の種類の名前 `work-kind` と、根拠の作業 `tasks` を持つ。

```
kind: procedure
work-kind: merge-main-into-branch
tasks: [app/20260105-101500-merge-main, web/20260110-143000-merge-main]   # <リポジトリ>/<作業 ID>
```

キーを分けるのは、学びの `pattern`（誤りの種類）や `cases`（事例）と意味を混ぜないためである。
本文の見出しは同じ五つにする。
現状には根拠の作業ごとの日付、リポジトリ、その場で書いた手順か飛ばした理由を書き、問題にはいちばん近い手順書と足りなかった点と分野に固有かを書き、期待する結果には手順書の案を書く。
見出しを分けないのは、選ぶ材料が五つに収まり、道具とレビューを変えずに済むためである。

ID は `<YYYYMMDD>-<hhmmss>-<slug>` にし、時刻は起票したときのローカルの時刻を秒まで入れる。ファイル名を並べると、起票した順に並ぶようにするためである。
連番は、番号を管理する状態が要り、並行するセッションの起票でぶつかるので採らない。
作業 ID も同じ形だが、起票と着手は別の時刻なので、着手するときは `log start --slug` で作業 ID を新しく付け、受け入れ条件の行 `pool:<ID>` で一件と結ぶ。

| 状態       | 意味                                | 動かす人                           |
| ---------- | ----------------------------------- | ---------------------------------- |
| `proposed` | 起票された候補                      | エージェント                       |
| `todo`     | 人間が着手を承認した                | 人間か、人間に頼まれたエージェント |
| `rejected` | 人間が却下した。理由を一行残す      | 人間か、人間に頼まれたエージェント |
| `done`     | main に入った。commit の SHA を残す | エージェント                       |

進行中の状態は持たない。着手した作業は、作業 ID の worktree と判断の記録で分かる。
`rejected` は消さずに残し、重複の照合の対象にする。却下したものが再び起票されないようにするためである。
`done` にするとき、道具は残す commit が main に含まれることを確かめる。
`rejected` への遷移は、環境変数 `CLAUDECODE` があると、却下を頼んだ人間の発言を `--quote` で求める。Claude Code はこの変数をコマンドに渡すので、エージェントが却下するときは必ずこの照合を通る。
道具は、引用が今の会話の最後の人間の入力（文章の発言か、選択式の質問への回答）に含まれ、引用の外に問いが無いことを確かめてから却下し、その入力を一件の `rejected_by` に残す。エージェントが自分の判断で却下できないようにするためである。
`rejected_by` に残るのは入力の全文ではなく、入力の ID（会話の記録の uuid）と引用した部分である。
無人の作業（`GORI_AUTO`）からは、発言を添えても却下できない。無人の作業の最後の発言は、作業を起動した道具の依頼文だからである。
`todo` への遷移は道具が拒まない。人間が会話で頼めば、エージェントが `todo` に上げられる。

人間は、会話でエージェントに頼むか、Claude Code の外の端末で `<gori>/tools/records/pool` を実行する。外の端末からの却下は、発言を照らさない。
PATH に通すことは、利用者のシェルの設定を変えるので入れない（`criteria/user-environment`）。

**起票先**：一件は、直すファイルのあるリポジトリのプールに入れる。人間が `pool list` を見るリポジトリと、着手して worktree を作るリポジトリを揃えるためである。
`pool add` は `--file` のパスで確かめる。すべて今のリポジトリにあれば今のリポジトリ、今のリポジトリに無くすべて gori のチェックアウトにあれば gori のプールに書く（gori の不備は、どのリポジトリで見つけても gori で直すため）。
これから作るファイルもあるので、親のディレクトリがあればあると見る。ただし最上位の一段のパスは、ファイルが実際にあるときだけあると見る。gori のプールに回すときは `--name` を断る。どちらにも無いパスがあるか、二つに分かれれば、起票先を推測せずに止まる。`--file` が無ければ今のリポジトリに書く。

重複の照合は、同じリポジトリのプールの全件を状態を問わずに照らす。
学びは、同じ `pattern` の一件があるかを道具が判定する。`proposed` か `todo` か `rejected` の一件があれば、道具は起票を断り、エージェントは `add-case` で事例を足す（`rejected` なら、却下したものがまた起きたと報告で伝える）。
`done` の一件があれば、`--recurrence-of` を付けて新しく起票し、本文に元の一件の対策の後に再発したと書く。直したはずのものが効いていないという新しい事実だからである。
改善候補は、`pool search` で当たりを出し、同じかどうかはエージェントが読んで決める。
手順書の候補は、同じ `work-kind` の一件があれば道具が起票を断る。名前は起票する側が既存の名前と読み比べて付ける。

## 3. レビューと改善ループの運用

### レビュアーのサンドボックスとレビュー結果の受け取り口

`tools/records/review --task <作業ID>` は、HEAD の commit の一時 worktree で、別セッションのレビュアー（`agents/reviewer`）を起動する（H-E5、H-E6、H-E8）。
レビュアーの Bash は OS のサンドボックスで動き、書けるのは一時 worktree、`review` が一時ディレクトリに作るレビュー結果の受け取り口、`/tmp/claude-<uid>` だけである。
作業リポジトリとその git の共通ディレクトリと、記録を置く gori のチェックアウトの全体（作業ツリーと `.git`）には書けない。
レビュアーは gori の道具を読んで動かすだけで gori の下に書く必要が無いので、記録、プール、知識ファイルをまとめて塞ぐ。
`review` は、task、sha、レビュアーのセッションを確かめたレビュー結果だけを記録の場所の `verdicts/` に取り込み、確かめられなければ未レビュー（終了コード 3）にする。
受け取り口が、作業リポジトリ、gori のチェックアウト、またはそれらの git の共通ディレクトリの中を指していれば、`verdict` は書かない。
人間は端末から `verdict record` でレビューしてもよい。
疑似端末で人間を装う、`GORI_CLAUDE_BIN` で偽のレビュアーを立てる、レビュー結果のファイルを手で置く、の三つは意図的な回避として防がない（`criteria/done`）。
完了と言ってよいのは `verdict check` が 0 を返すときだけで、1 から 4 の扱いは `criteria/done` にある。

### レビューの範囲と E2E

レビューの範囲の起点は、start 行の `base=` にしている。start 行の時刻から推すと、同じ秒の commit で揺れるためである。
レビューする commit がローカルの main（無ければ master）の先端を含まなければ、`review` はレビュアーを起動せず終了コード 2 で止まり、載せ直すよう示す。古い位置でレビューすると、取り込みの載せ直しで commit が変わり、レビューをやり直すことになるためである。
HEAD をレビューするときに作業ツリーに未コミットの変更か未追跡のファイルがあれば、`review` はレビュアーを起動せず終了コード 2 で止まり、そのファイルを示す。`verdict record` がその状態のレビュー結果を断り、レビュアーには作業ツリーを直せないためである。
レビューする commit に、自己点検の行（`log add --type check --criterion <指し>`）が欠けていても、`review` はレビュアーを起動せず終了コード 2 で止まり、欠けた指しと書き方を示す（`--dry-run` でも同じ）。要る指しは、有効な受け入れ基準のそれぞれ（accept 行は `行 N`、`pool:<ID>` の行は条件ごとに `行 N#k`）、最後の承認の行（`承認`。無人の承認では要らない）、範囲の差分が `.md` を変えるときの `文書` である。check 行の result には、道具が点検したときの HEAD の SHA を入れ、`review` はレビューする commit の SHA を持つ行だけを数える。点検せずに出して不合格になる往復を防ぐためである。
レビュアーの中では、claude を起動できず、疑似端末を開けず、一時 worktree と `/tmp/claude-<uid>` の外へ書けない。
そこで `review --e2e <相対パス>` は、レビューする commit の別の一時 worktree で、作業者の身元を消した環境でサンドボックスの外からスクリプトを走らせ、終了コードと全出力をレビュアーに渡す。
受け入れ条件を書く時点でサンドボックスで確かめられない条件を見分け、`tests/e2e/` のスクリプトの通過として書く規則は `skills/decision-log` にある。

### レビューの重さ

文書だけを直す変更と、道具の検査を変える変更が、同じ重さのレビューを受けていた（一週間で 229 回、10.7 時間）。
そこで `review` は、範囲の差分のファイルから重さを決める（`tools/lib/weight.mjs`）。作業者の申告は使わず、被害の大きい変更が軽い側に落ちないよう、軽い側を狭く決める。
軽い（light）のは、変えたファイルがすべて `*.md` で、`knowledge/`、`agents/`、`hooks/`、`tools/`、`tests/`、`.claude/`、`.claude-plugin/` の下（入れ子のフォルダも含む）にも、`CLAUDE.md`、`AGENTS.md` にも当たらないときだけである。gori の知識ファイルとエージェントへの指示は、文書でも以後の作業の振る舞いに効くのでふつうにする。`--e2e` を付けた依頼もふつうにする。
軽い側もレビューは残す。レビュアーは `config/models` の reviewer-light のモデルで、テストを全部は走らせず、差分が書いた事実を実物と照らして受け入れ基準を確かめる。文書の事実の食い違いを不合格にする基準（`agents/reviewer`）は軽い側でも変わらない。
重さはレビュー結果の `weight` と、判断の記録のレビュー結果の行の why に残り、`metrics` の `review-light` で数える。

### main の取り込みと合格の引き継ぎ

合格した commit に `sync-main` が main を merge すると、SHA が変わるのでその合格は使えない。
並行の作業では一つが main に入るたびにほかの作業がこうなり、取り込んだ変更が自分の変更と関係なくても、全体のレビューをやり直すことになる。
そこで `verdict check` は、HEAD にレビュー結果が無くても、次をすべて満たす merge commit なら、一つ目の親の合格を引き継いで 0 を返す（`tools/lib/audit.mjs` の `carriedState`）。
親が二つで、一つ目の親がこの作業で合格し（引き継いだ合格でもよい）、二つ目の親が main に含まれる。HEAD の木が `git merge-tree` の自動の merge の結果と同じである。作業と main が、二つの親の merge-base から変えたファイルが重ならない。
手で衝突を解いた merge、merge commit に変更を足したもの、重なる取り込みは、今までどおり全体をレビューする。
対象が変われば判定を無効にする H-E5 を、この形に限って緩めている。ファイルが重ならなくても意味の上でぶつかる取り込み（main が名前を変えた関数を作業が呼ぶなど）は、取り込んだ後の検証のやり直しだけが拾う。
main に入った merge commit の一つ目の親が合格した commit なので、合格は git の履歴から辿れる。

### 確認できずと受け入れ条件の取り下げ

解く問題は、レビューが成果の良し悪しではなく、レビュアーが確かめる手段を持たないことと、途中で古くなった受け入れ条件のために不合格になり、レビューをやり直すことである。
合格には、直すことを勧める指摘（`suggestions`、`verdict record --suggest`）を添えられる。`verdict check` は 0 のままその指摘を出し、担当がその指摘をどう扱うかは `criteria/done` が決める。
不合格の findings と欄を分けるのは、事例の抽出が不合格と確認できずの findings だけを読み、勧める指摘を誤りとして数えないためである。不合格にする基準は `agents/reviewer` にあり、文書に書いた事実と実物の食い違いは不合格に残している。

**確認できず**：レビュアーが、確かめる手段を持たない基準があると記録するレビュー結果。値は `unverified` で、`pass`、`fail` と並ぶ三つ目の結果にする。
満たしていない基準が一つでもあれば `fail` にし、それが無く、確かめられない基準があるときだけ `unverified` にする。
`fail` の指摘の一つずつに種類を付ける案は、指摘の形が文字列から構造に変わり、結果を読む道具と過去の記録の読み方をすべて直すので採らない。
レビュアーが結果を記録せず未レビューで終える案は、足りない材料が記録に残らず、起動の失敗と見分けられないので採らない。

確認できずのとき、`verdict check` と `review` は終了コード 4 を返し、確かめられなかった基準と足りない材料を示す。
担当は成果を直さず、材料を足してレビューを依頼し直す。E2E を渡していなければ `--e2e` を付けて同じ commit で依頼し、E2E のスクリプトが無ければ足して commit してから依頼する。
担当が材料を足せないときは、止まって人間に報告する。人間は端末から `verdict record` でレビュー結果を記録できる。
未レビューの 3 に含めないのは、3 が止まって人間に報告する決まりで、担当が自分で材料を足して続ける動きと混ざるためである。
4 のままでは、作業を完了にできない。

確認できずの記録には、指摘（確かめられなかった基準と、何があれば確かめられるか）と、証拠（試したコマンドとその出力）の両方を道具が求める。
`agents/reviewer` は、試さずに確認できずにしないことと、確かめられた基準には合格のときと同じく証拠を付けることを決めている。
同じ作業で確認できずが二回続いたら、`review` は三回目を起動する前に止まり、人間に報告するよう示す。材料を足しても確かめられない基準は、人間が自分で確かめるか、受け入れ条件を見直すかを決める。
選べる理由を道具で一覧に固定する案は、一覧に無い事情が出るたびに道具を直すことになるので採らない。

`tools/learning/metrics` は、確認できずを `verdict-fail` と別の指標で数える。成果の不備と、確かめる手段の不足を、数の上で分けるためである。
抽出は、確認できずも事例の材料にし、事例の種類を `verdict-fail` と分けた `verdict-unverified` にする。受け入れ条件の書き方や渡す材料の不足は、繰り返せば手順や道具で直せる誤りだからである。
再レビューの依頼文には、前回が確認できずのときもその指摘を渡し、足りなかった材料が今回あるかを先に確かめさせる。

**取り下げ**：判断の記録の fix 行に足す形で、`行 N を取り下げ: <理由>` と書く。取り下げた受け入れ条件は、レビュアーに基準として渡さない。
作業の途中で実装の方針が変わったら、担当は古い条件を取り下げ、新しい条件を足し、人間の承認をもらい直す。
取り下げだけをした後も、承認の行が無ければ `review` はレビュアーを起動しない。担当が都合の悪い条件を黙って外すことを防ぐためである。
受け入れ条件がすべて取り下げられていれば、`review` はレビュアーを起動しない。
`skills/decision-log` は、方針が変わったら実装を続ける前に条件を直して承認をもらうよう決めている。
条件をまとめて入れ替える行を足す案は、変わっていない条件まで書き直すことになるので採らない。新しい作業として始め直す案は、作業 ID に結びついたブランチと worktree から実装を移す手間が出るので採らない。

プールの一件から始めた作業で方針が変わったら、担当は `pool:<ID>` の行を取り下げ、今も有効な条件と新しい条件を、ふつうの accept 行として書き直す。
プールの本文は書き換えず、起票したときに求めていたことを残す。作業が main に入れば、その一件は今までどおり `done` にする。
プールの受け入れ条件を担当が書き換える操作を足す案は、人間が `todo` にした一件の中身を担当が後から変えられることになるので採らない。

レビュアーへの依頼文は、受け入れ基準の節に有効な条件だけを並べ、取り下げた条件と理由は「取り下げた条件（基準ではない）」の節で知らせる。
取り下げがある作業の依頼文には、作業の目的と受け入れ基準が食い違うときは受け入れ基準を優先する、と書く。作業を始めたときの目的が古くなっていても、それを理由に不合格にしないためである。
取り下げた条件を見せない案は、レビュアーが、人間の承認が変更を含んでいるかを確かめられないので採らない。

### 改善ループと抽出の運用

**改善ループ**：抽出が学びを `proposed` で起票し、人間が `todo` に上げ、人間がセッションごとに一件を指して `procedures/feature` で進め、レビューの後に取り込む流れ（H-I2、H-I4）。
人間が一件を指さなくても `todo` の一件が始まる形は、「自律起動」の節で決めた。
並行して進めるときは、セッションを複数立てる。作業 ID ごとに worktree が分かれ、同じファイルを変える作業は、後の方が main の上に載せ直してからレビューを受ける（`criteria/done`）。
同時に進める件数の上限は持たない。上限を持つと、占有と生存の追跡、復旧、件数の数えが要るためである。
作業リポジトリでは、リモートが無ければ、レビューに合格した commit を main に fast-forward で取り込み、その一件を `done` にする。リモートがあれば draft PR を作る。
gori 自身の変更は、リモートがあっても PR を経ずに手元の main に取り込む（次の節）。
道具の変更も知識ファイルの変更と同じく以後のすべての作業に効くので、どちらも `procedures/harness-change` で人間の承認を挟む。
計画に沿った開発は手順書で進め、プールに起票するのは抽出が見つけた学びと手順書の候補と、作業の中で見つけた不具合や改善の候補に限る（`config/routing`）。

SessionEnd フック（`tools/hooks/session-end`）は、一定の間隔で（既定値はこのフックの中にある）、`tools/learning/extract-run` を切り離して起動し、`extract-run` はそのマシンのチェックアウトで `claude -p "/gori:extract"` を走らせる（H-I10）。
抽出とレビューのセッションでは起動せず、ルートが gori のチェックアウトでなければ理由をログに書いて終わる。
人間は `extract-run --session <ID>` で、抽出を指定したセッションに絞れる。
SessionEnd フックは、終わった会話を抽出待ち（`learning/pending/`）に積み、`tools/learning/sessions --unprocessed` はこの一覧だけを材料にする。
フックは gori が読み込まれた会話でしか動かないので、積まれた会話は gori の会話で、かつ終わった会話である。
そのうえで、抽出の能力を呼んだだけのものと、`claude -p` で起動したもの（`entrypoint` が `sdk-cli`。レビュアーも含む）を、人間がその場で訂正した会話ではないので材料から外す。
会話の記録の全体を走査して選ぶ形は、推す規則の直しが続くので採らない。フックが動かずに終わった会話は読まれないが、抽出は材料の一部を読めれば足りる。
`skills/extract` は、三つの観点を `agents/extract-reader` に別々のモデルで読ませて事例を書き、二件以上の `pattern` だけを起票する。
`tools/records/trace <作業ID>` は、判断の記録、レビュー結果、人間の発言（done の後も含む）を作業 ID でつないで時刻順の JSONL にする。
主な読み手は抽出の能力と `tools/learning/metrics` なので、機械が読む JSONL を正とし、人間向けの表示は `--text` の整形にとどめる。
`trace` は、作業の commit を出さない。履歴を畳むと古い commit は読めなくなるので、作業が終わった後に commit を git に問い合わせない。

**手順書の候補**：その場で手順を書いた作業や、手順書が合わなかった作業が繰り返されても、手順書にする候補として人間の目に届かない。
これを拾う能力が `skills/procedure-scout` で、材料は `tools/learning/procedure-material` が集める。
学びとは選ぶときの目が違うので、能力もプールの種類も分ける。
`extract-run` は `/gori:extract` の後に続けて `/gori:procedure-scout` を走らせ、人間も手で呼べる。起動のモデルは `config/models` の `procedure-scout` の行で決める。
抽出が失敗しても走らせるのは、手順書の候補が抽出の結果を使わないためである。
`--session` のときと、表に行が無いときは走らせず、理由をログに書く。`--session` は抽出をセッションに絞る指定で、手順書の候補はセッションと関わりが無いためである。

材料は全リポジトリの判断の記録で、会話の記録は読まない。
拾うのは、その場で書いた手順書で始めた作業（start 行の evidence が `stdin`）と、手順書が想定していない事情で手順を飛ばした作業である。
手順の中の当てはまらなければ飛ばす分岐を通っただけの step-skip は拾わない。step-skip を件数で絞らないのは、2026-11-08 に数えたとき大半がこの分岐で、件数では見分けられなかったためである。
どこまで読んだかの印は持たず、毎回全件を読み直す。材料が小さく、二重の起票は `work-kind` の照合で防げるためである。
委任はせず、起動したセッションが自分で読む。抽出が観点ごとに読み手を分けるのは会話の記録が長いためで、判断の記録には当たらない。

拾った作業のうち既存の手順書で足りたものを除き、残りを作業の種類ごとにまとめる。既存の手順書と同じ種類かは、索引を読んで決める。
同じ種類の作業が二件以上あればプールに起票し、一件のものは報告に一行で知らせる。これまでの手順書は一件のうちに人間が選んだものだったので、一件でも選べる道を残す。
分野に固有の作業も起票し、手順書にするかは人間が選ぶ。
`todo` に上がった一件は `procedures/harness-change` で手順書にする。
来歴の `source` には、どんな作業の種類から手順書にしたかを一文で書き、作業 ID は書かない。公開する知識ファイルに手元のリポジトリの名前を入れないためで、根拠はプールの一件の `tasks` で辿れる。

### 自律起動（H-E11）

解く問題は、`todo` の一件があるのに、人間がセッションを開いて指示するまで作業が始まらず、始まっても受け入れ条件の承認で止まって放置されることである。
人間が決める場所を、一件を `todo` に上げるときと、合格した成果を取り込むときの二か所に絞り、その間を無人で進める。学びの一件に限り、取り込みも無人で行う（「止める場所」）。

**承認**：人間が一件を `todo` に上げたことを、その一件の本文の受け入れ条件の承認として扱う。
無人の作業は、受け入れ条件の行が `pool:<ID>` だけのときに限り、承認の行が無くてもレビューに出せる。
担当が受け入れ条件を足すか取り下げたら、無人では続けず、止まって人間に知らせる。人間が見ていない条件でレビューに出さないためである。
gori 自身の知識ファイルや道具を変える作業も同じ扱いにする。変更の中身は、main に入れる前に人間が確かめる。
gori 自身の変更だけ途中の承認を残す案は、`todo` の一件がすべて gori のプールにあり（2026-11-13 時点で 13 件、ほかのリポジトリは 0 件）、無人で進む作業が無くなるので採らない。

**きっかけ**：無人の作業を始めるきっかけは、プールの `todo` の一件のうち、kind が learning の一件（学び）だけにする（2026-11-14 に決めた）。
kind が improvement と procedure の一件は、`todo` でも無人では選ばず、人間が会話で進める。人間がそう決めた。この種類は手順書、能力、道具を新しく足す機能の追加で、無人で合格まで進めても、取り込む前に人間が中身をすべて読むことになるためである。
GitHub の Issue から始めたい作業は、人間がプールに起票して `todo` に上げる。
ラベルを付けた Issue をきっかけに足す案は、受け入れ条件の正本がプールと Issue の二か所になるので採らない。remote のある三つのリポジトリで、Issue は一件も作られていなかった（2026-11-13 に `gh issue list --state all` で確かめた）。

**一回分の道具**：kind が learning の `todo` の一件を一つ選び、`claude -p` で一件だけ進める道具（`tools/auto/run`）を作る。
動かす場所は手元のマシンに限る。プールと記録が手元の gori のチェックアウトにしか無いためである。
`pool:<ID>` の受け入れ条件の行を持ち、done の行が無い作業がある一件は、着手済みとして選ばない。人間が会話で進めている作業も、止まって人間を待っている無人の作業も、この判定で避けられる。
担当が受け入れ条件の行を書く前に止まると、この判定では結び付かない。そこで道具は、`claude -p` の結果のセッション ID が start の行を書いた作業のうち、作業 ID がその実行を始めた時刻より後のものを、その実行の作業として記録する。作業 ID は `log start` が始めた時刻から付けるので、担当が古い時刻の作業 ID を渡して始めた作業は結び付かない。実行の記録が作業を指し、その作業に done の行が無い一件も、選ばない。
プールに進行中の状態を足す案は、止まった作業の状態を戻す片付けが要るので採らない（2 章「改善候補のプール」）。
道具は、gori の記録の場所に置くロック一つで、同時に一つだけ走る。見つけてから判断の記録を作るまでの間に二つの起動が同じ一件を選ぶことを防ぐためである。持ち主のプロセスが死んでいるロックは、古いものとして取り除く。
作業者とレビュアーのモデルは、`config/models` の表をそのまま使う。

**止める場所**：無人の作業は、どのリポジトリでも、レビューに合格したところで止まり、作業のブランチと worktree を残して終わる。
draft PR の作成と main への取り込みは、人間が頼んだときに `skills/work-branch` の手順で進める。main への取り込みと外への送信は、取り消せない操作だからである（`criteria/autonomy`）。
gori 以外のリポジトリだけ最後まで進める案は、取り消せない操作を人が見ないまま行うので採らない。

例外として、gori のプールの学び（kind が learning の一件）は、合格した成果を無人で手元の main に取り込む（2026-11-14 に決めた）。
解く問題は、根拠のある小さな直しまで人間の取り込みを待ち、学びが効き始めるのが遅れることである。
学びは、二回以上起きた誤りを根拠に既存の部品を直すものなので、人間が中身を見ないまま入る変更をこの種類に限る。
線は種類で引く。道具が種類を読むだけで判定でき、無人の作業が自分で改善だと判断する余地が無いためである。
ほかのリポジトリのプールの学びは、合格で止まる。
`todo` に上げるときに人間が一件ごとに印を付ける案は、上げるたびに判断が一つ増えるので採らない。プールの一件をすべて無人で取り込む案は、新しい部品が人間の見ないまま以後のすべての作業に効くので採らない。

取り込むのは一回分の道具であり、作業者ではない。作業者は柵の中のままで、main を動かせない。
一回分の道具は、作業者が終わった後に、次のすべてを確かめてから取り込む。一つでも欠ければ、取り込み待ちとして止まる。

- その一件が gori のプールにあり、kind が learning で、今も `todo` である。
- 受け入れ条件の行が `pool:<ID>` の一行だけで、訂正も取り下げも無い。
- レビューに合格している（`verdict check` が 0）。
- 作業のブランチが、手元の main に fast-forward で入る。main が先に進んでいたら、載せ直しは人間に委ねる。
- 手順書の手順が、最後の二つより前に残っていない。作業者は、main に取り込む手順とプールの一件を `done` にする手順だけを残して終える。それより前の手順が残っていれば、作業が終わっていないものとして扱う。
- 一回分の道具が、無人の作業の中から呼ばれていない。

取り込んだら、プールの一件を `done` にし、残した手順を済みにして判断の記録に done を書き、worktree を片付ける。push はしない。
取り込んだ後の記録に失敗しても main は戻さず、残ったことを実行の記録と知らせに出す。
作業者の実行の間に main が動いていたら、今までどおり失敗として残し、取り込まない。
手元の main への取り込みは、push するまでは `git revert` で戻せる。

**窓口**：人間とのやり取りは、名前を固定した一つのセッションに集める。
人間は毎朝、`claude -n gori-auto "/gori:auto"` で新しいセッションを窓口として立てる。
窓口は、見回りのスクリプト（`tools/auto/watch`）をバックグラウンドで走らせる。スクリプトはモデルを使わず、起動してすぐと、その後は `config/auto` の watch-minutes の間隔で、一回分の道具を呼ぶ。`todo` の一件を選ぶのも、上限を確かめるのも、一回分の道具である。
バックグラウンドの命令は、セッションを終えると止められる（公式の文書）。そこで、窓口は立てるたびに見回りのスクリプトを起動する。起動の指示は窓口の能力（`skills/auto`）に書き、立てる一行の `/gori:auto` がそれを呼ぶ。
前日のセッションを `claude -r gori-auto` で開き直す案は、窓口が会話に状態を持たないので引き継ぐものが無く、会話が日ごとに長くなるので採らない。日中に誤って閉じたときも、同じ一行で立て直す。
知らせることができたとき（合格、残ったことのある取り込み、停止、失敗、一日の上限）だけスクリプトが終わり、窓口のモデルが起きて人間に伝える。一回分の道具が結果を出さずに落ちたときも、失敗として終わる。進める一件が無い間と、別の一回分の道具が動いている間は、待って続け、トークンを使わない。
学びを無人で取り込んだときは、知らせずに、待たずに次の一件を見る。取り込んだ後の記録に残ったことがあるときだけ、終わって知らせる。人間が直すことがあるためである。
終わるときは、人間の対応が要るものの一覧（`tools/auto/status` の内容）を出す。
人間は窓口で、取り込みと再開を頼む。窓口は会話の中に状態を持たず、毎回プールと記録から読み直す。
見回りが合格、残ったことのある取り込み、停止で終わったら、窓口は人間に伝えて見回りを起動し直す。失敗と一日の上限で終わったら、起動し直さない。同じ失敗を繰り返して上限を使い切らないためである。
バックグラウンドの命令が終わると、人間の入力を待っているセッションのモデルが起きることは、4 分後に終わる命令で確かめた（2026-11-13。公式の文書には無い）。
窓口は、人間が朝に立て、夕方に閉じる使い方を前提にする。何日も開いたままにする使い方は前提にせず、そのときの動きは確かめていない。
窓口を閉じている間は、無人の作業は始まらない。launchd や cron への登録は、利用者の環境の設定を変えるので作らず、案内も書かない（`criteria/user-environment`）。
窓口のセッションごと安いモデルで立てて定期的に起こす案は、何も無くてもトークンがかかり、main への取り込みを含む指示まで安いモデルが進めるので採らない。

**知らせ**：止まった作業は、判断の記録に pause の行で理由を残し、人間が再開を頼めば `skills/resume` で続きから進む。
止まるのは、受け入れ条件を直す必要が出たとき、レビューが未レビューで終わったとき、確認できずが二回続いたとき、条件が曖昧で観察では決められないときである。
人間の対応が要るものは、`tools/auto/status` が、実行の記録と判断の記録から出す。取り込み待ちの作業（レビューに合格し、done の行が無い）、人間を待って止まった作業（合格しておらず、done の行が無い）、直近の失敗（最新の実行の記録が失敗か、結果を書く前に切れた）の三つである。
合否は、実行の記録に残した値でなく、今のレビュー結果で決める。止まった作業を人間が会話で再開して合格させたら、取り込み待ちに移る。
無人で取り込んだ作業は、知らせない。人間が要らないと決めた（2026-11-15）。実行の記録には、取り込んだことと commit を残す。
SessionStart フックは、窓口を閉じていた間の控えとして、これらを当てはまるときだけ一行ずつ足す。無人の作業、抽出、レビューのセッションには足さない。
macOS の通知と、Slack やメールへの送信は足さない。合格も停止も、人間が次に窓口を開いたときに対応すれば足りるためである。

**無人の作業の柵**：一回分の道具は、無人であることを示す環境変数を付けて `claude -p` を起動する。
印は `GORI_AUTO=1` である。
その印があるとき、次の四つを道具で拒み、印を読めないときも拒む側に倒す（H-E10）。

- プールの一件を `todo` に上げることと `done` にすること、`rejected` にすること。`todo` を承認として扱うので、無人の作業が上げられると、自分で自分を承認できる。却下は人間が決めることで、無人の作業の最後の発言は人間の発言ではない。
- main を動かすこと（マージ、fast-forward、main への commit）。
- 外への送信（`git push`、PR の作成など）。
- 承認の行を書くこと。無人の作業には人間の発言が無く、書ければ偽の承認になる。

四つは、この節が人間の決める場所とした操作である。学びの一件の取り込みは、柵の外にいる一回分の道具が行うので、柵は変えない。
プールの遷移と承認の行は、`pool` と `log` が印を見て拒む。印は値を見ず、変数があれば無人として扱う。
main を動かす操作は git の reference-transaction フックで、push は pre-push フックで拒む（`tools/auto/githooks/`）。
フックは印で分岐させず、柵のフックの置き場所を git の設定として環境変数で渡したときだけ効く。渡す環境は `tools/lib/auto.mjs` が作り、一回分の道具がそれを使って起動する。リポジトリの設定を書き換えないので、gori のフックを入れていないリポジトリでも導入なしで効き、人間の作業はこのフックを読まない。
柵のフックの置き場所はリポジトリのフックの置き場所を上書きするので、リポジトリが元から持つ pre-commit と commit-msg は、柵のフックから呼ぶ。
呼ぶのは、リポジトリの設定の `core.hooksPath` か `.git/hooks` にあるこの二つだけである。利用者のグローバルな設定の `core.hooksPath` にあるフックと、ほかの種類のフック（prepare-commit-msg など）は、柵のもとでは呼ばれない。
git merge と git pull は ref を更新する前に作業ツリーとインデックスを書き換えるので、柵のフックは、それを拒んだときに二つの木の切り替え（`git read-tree -m -u`）で戻す。前からあった未 commit の変更は残る。commit は作業ツリーを書き換えないので戻さない。
それでも本体のチェックアウトが変わることはあるので、一回分の道具は、起動の前と後で、本体のチェックアウトの main の位置と未 commit の変更を比べ、違えば失敗として残す。
PR の作成は、`gh` の設定の場所（`GH_CONFIG_DIR`）を空のディレクトリに向けて起動し、`gh` を未ログインにして防ぐ。空のディレクトリで `gh` が未ログインになることを確かめた。
`claude -p` の `--plugin-dir` には、gori のチェックアウトでなく、gori の記録の場所の `auto/plugin` に置いた main の detached の worktree を渡す。一回分の道具が、実行のたびに main の先端に合わせる。
Claude Code は `--plugin-dir` の下のファイルを Write と Edit で書かせず、許可の設定を足しても変わらないため、チェックアウトを渡すと、その下の `.worktree/` にある gori の作業の worktree の知識ファイルを書けない（2026-11-15 に試して確かめた）。
その代わり、本体のチェックアウトのファイルへの Write と Edit も拒まれなくなる。これは防がず、上の起動の前と後の比較で気付く（人間が 2026-11-15 に決めた）。
`claude -p` の起動には、`git push` と `gh pr create` を拒む指定（`--disallowedTools`）も重ねる。公式の文書は、この指定が別の書き方の呼び出し（`git -C . push` など）に当たらず、安全の境界にならないと書いているので、これだけには頼らない。
フックは、無効にする指定（`-c core.hooksPath`）を付けるとすり抜ける。柵は誤りを止めるもので、意図的な回避は防がない。レビューの回避を防がないのと同じ立場である（「レビュアーのサンドボックスとレビュー結果の受け取り口」）。
人間が会話で進める作業には、柵を足さない。4 章の「道具による強制」の見送りは、人間が見ている作業についてそのまま残す。
OS のサンドボックスで書ける場所とネットワークを絞る案は、依存の取得のようなネットワークが要る作業が無人で進まなくなるので、四つの柵で防げない誤りが出たときに決め直す。

**費用の上限**：無人の作業の費用は、三つの層で抑える。
解く問題は、`claude -p` の利用が意図せず多額の請求になることである。
公式のサポートの記事は、サブスクリプションでログインした `claude -p` の利用はプランの利用の枠から引かれ、追加利用（extra usage）が無効なら使えるのはプランに含まれる利用だけだと書いている（2026-11-13 に委任先が読んだ。2026 年 6 月 15 日に予告されていた変更は保留されている）。
請求が生じるのは、API キーなどで従量課金に切り替わったときと、追加利用が有効なときである。三つの層のうちアカウントの層が、この二つを塞ぐ。

- アカウントの層：一回分の道具は、ログインが claude.ai のサブスクリプションであることを起動のたびに `claude auth status` で確かめ、確かめられなければ起動しない。サブスクリプションより優先される認証の環境変数（`ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、`CLAUDE_CODE_USE_BEDROCK`、`CLAUDE_CODE_USE_VERTEX`、`CLAUDE_CODE_USE_FOUNDRY`）と `ANTHROPIC_BASE_URL` は、取り除いてから `claude -p` を起動する。設定に `apiKeyHelper` があれば起動しない。追加利用を無効にすることは、人間がアカウントの設定で行う。gori からはその設定を確かめられないが、人間が無効であることを確かめた（2026-11-13）。
- 一回の層：一回分の実行に、金額の上限（`--max-budget-usd`）と時間の上限を付け、超えたら止めて、止まった作業として知らせる。レビュアーの起動にも金額の上限を付ける。金額の上限はサブスクリプションのログインでも働き、超えた実行は `error_max_budget_usd` で終わる（2026-11-13 に試した）。判定は応答の区切りで行われるので、上限を一つの応答の分だけ超える。上限 0.0001 ドルの試しは 0.0078 ドルで止まった。
- 一日の層：一回分の道具が、その日に起動した回数を自分の実行の記録から数え、上限に達していれば起動しない。判断の記録には無人で始めた作業かどうかの印が無く、金額を残す実行の記録がどのみち要るので、そこから数える。

アカウントの層は gori の外にあるので、gori の不具合があっても超えない。
一回の層と一日の層は、無人の作業がサブスクリプションの枠を使い切り、人間が会話で進める作業ができなくなることを防ぐ。
gori の中の二つの層だけにする案は、上限を守るのが gori のコードだけになるので採らない。アカウントの層だけにする案は、一件の作業が暴走したときに枠を使い切るまで止まらないので採らない。

値は `config/auto` の表を正本とし、この文書には書かない。一回の時間は `run-minutes`、作業者とレビュアーの一回の金額は `worker-budget-usd` と `reviewer-budget-usd`、一日に無人で始める件数は `runs-per-day` である。
時間は、プールの一件から始めて完了した 30 件の中央値 17 分（人間の待ち時間を含む）の約 3 倍を目安にした。
金額は実績に基づかない仮の値である。会話の記録に金額が無いためで、一回分の道具が実行ごとの金額を記録し、数件たまったら見直す。
サブスクリプションで動かす場合、この金額は請求額ではなく、使った量を API の定価で換算した値である。
道具は `config/auto` の表を機械的に読み、値を読めないときは起動しない。
一回分の道具は、実行ごとに、選んだ一件、終わり方、金額、かかった時間を、gori の記録の場所の `auto/runs/` に一件ずつ残す。会話の中身は写さない。
金額は作業者の起動の分で、作業者が起動したレビュアーの分は含まない。
0 以外の終了、時間切れ、金額の上限での停止、main か作業ツリーの変化は、失敗として残す。
アカウントの層で起動しなかった失敗も、見回りと知らせから気付けるよう記録に残し、一日の回数には数えない。
無人の作業がこのファイルを書き換えても、効くのは人間が main に入れた後である。

**今の記述との関係**：2 章「記録」の、承認の行が無ければ `review` がレビュアーを起動しない検査は、上の「承認」の条件のときだけ通す。条件は、印があり、受け入れ条件の行がどれも `pool:<ID>` で、訂正も取り下げも無く、その一件が今も `todo` であることである。
`procedures/learning-apply` と `procedures/harness-change` の、変更の中身の承認で止まる手順は、無人の作業では main に入れる前の確認に移す。
この扱いは手順書には書かず、一回分の道具が作業者に渡す依頼文の一か所に書く。同じ決まりを手順書ごとに書くと、食い違うためである。

**確かめていないこと**：プランの利用の枠を使い切ったときに `claude -p` がどう終わるか（エラーの形、終了コード）は、公式の文書に無く、試していない。一回分の道具は、0 以外の終了をすべて失敗として知らせる。

### 公開と上流

gori は GitHub の公開リポジトリで配る。
上流のマシンは、そのリポジトリの clone で gori を育て、改善を push する。ほかのマシンは、clone した gori を独自に育てる。

公開リポジトリは、手元の履歴を含めない一つの初期 commit から始める。
手元の履歴を持っていたチェックアウトは、別の名前に移して残し、同じパスに公開リポジトリを clone し直して、学び、プール、記録（`.git/gori/`）を新しい `.git` の下に移す。
新しい `.git` に手元の履歴が無いので、誤った push で手元の情報が出ることが無い。
手元の履歴を同じ `.git` に残して main だけを付け替える案と、手元の履歴を書き換えて公開する案は、誤った push と消し漏れを防げないので採らない。

push する中身は、push の前の git のフック（`tools/repo/githooks/pre-push`）が、検査の道具（`tools/repo/check-public`）で必ず確かめる。
道具は、追跡しているファイルと、push する commit のメッセージとその commit が足した行で、ホームの下の絶対パス、メールアドレス、秘密らしい文字列、手元だけの禁止語を探し、当たれば push を止める。
禁止語の一覧（ほかのリポジトリの名前のような、マシンごとに違う語）は、それ自体が手元の情報なので commit せず、`.git/gori/` の下に置く。
手順書で走らせる形は走らせ忘れると公開され、GitHub の上の検査は公開された後に見つかるので、フックにする。
最初の公開だけは、初期 commit を作る前に、入れるファイルの一覧と検査の結果を人間に示し、承認を得てから初期 commit を作って push する。

gori 自身の変更は、PR を経ずに、レビューに合格した commit を手元の main に fast-forward で取り込む。
gori を直すのは上流のマシンの持ち主一人で、レビューの合否は記録に残るので、PR を作っても確かめることは増えない。
GitHub への push は外への送信なので、人間が指示したときか、人間が自分で実行するときだけ行う（`criteria/autonomy`）。

手元の main の履歴は、畳んでよい。`tools/repo/squash-history` が、ツリーを変えずに、親の無い一つの commit に置き換える。
そのため、記録は、作業が終わった後に commit の SHA を git に問い合わせない。学びの適用日はプールの一件の `updated` から読み、`trace` は commit を出さない。
レビュー結果と commit の結び付きを使うのは、作業を始めてから main に取り込むまでの間だけである。その間は、レビューを受けた commit を書き換えない。
`squash-history` は、main の他にローカルのブランチがあるとき、未 commit の変更があるとき、無人の作業が動いているときは、畳まずに止まる。

上流の更新を merge で取り込む手順は持たない。上流の履歴が畳まれると、merge の起点になる共通の commit が残らないためである。
ほかのマシンは、手元で育てたものと上流を比べ、欲しいところだけを任意で取り込む。
会話を始めるたびに上流と比べる仕組みは、毎回ネットワークに出るので持たない。

ほかのマシンと、履歴を畳んだ後の上流のマシンでは、手元の main と GitHub の main が分かれるのが普通の状態になる。
そこで、main を取り込む道具（`tools/repo/sync-main`）と worktree を作る道具（`tools/repo/worktree`）は、分かれていても止まらず、手元の main を使って続け、分かれていることを一行出す。作業の報告で、その一行を人間に伝える。
手元の作業に要るのは手元の main だけである。
手元の main が origin より先に進んでいるだけなら、分かれていないので何も出さない。
上流を取り込まないと決めたマシンは、環境変数 `GORI_IGNORE_UPSTREAM=1` で宣言する。二つの道具は origin を fetch せず、比べず、手元の main を進めず、一行も出さない。宣言したマシンで origin に手元の main を進めさせないのは、それも上流の取り込みに当たるからである。

上流の更新が手元のデータ（`.git/gori/` の下）の形を変えるときのマイグレーションの仕組みは、まだ無い。
それが作られるまでは、データの形（記録、プール、学びの置き場所や書式）を変える変更を push しない。

### 効果の測定

`tools/learning/metrics` は、週（ISO 週、月曜始まり、ローカル時刻）ごとに、五つの数を `week`、`metric`、`key`、`count` の TSV で出す（`--text` は表、H-I12）。

- `cases` は `pattern` ごとの事例の件数で、事例 id の日付の週に数え、取り消した事例を除く。取り消しの規則は `tools/learning/case` の `list` と `count` と同じ部品（`tools/lib/learning.mjs`）を使う。
- `step-skip` は step-skip 行の数で、行の time の週に数える。`key` は `<手順書>#<番号>:<手順の文の先頭 20 字>` で、どの手順書のどの手順が飛ばされたかを読めるようにする。番号は作業を始めたときの手順書のものなので、文の先頭で版の違う手順を分ける。その場で書いた手順書の作業は、番号が作業ごとに別の手順を指すので `-` にまとめる。手順書は `trace` の start 行の `procedure` から取る。
- `verdict-fail` はレビュー結果の不合格の数で、レビュー結果の time の週に数える。
- `verdict-unverified` はレビュー結果の確認できずの数で、レビュー結果の time の週に数える。
- `review-light` は、軽い重さ（`weight` が `light`）で受けたレビュー結果の数で、レビュー結果の time の週に数える。

記録を直接読む集計を別に持たない。
作業の一覧だけを記録の場所の判断の記録のファイル名から取り、判断の記録とレビュー結果は作業ごとの `tools/records/trace` の出力から数える。
訂正の回数は会話の記録ではなく事例から数えるので、会話の記録が消えた期間も数えられる。
`trace` には空の `--projects` を渡し、会話の記録を読ませない。
最後の commit にレビュー結果の無い作業の数は数えない。未レビューのまま done にすることは、`log` が done を書くときに拒む。
`metrics` は `--root` のリポジトリの記録だけを数える。

`metrics --learnings` は、週ごとの数の代わりに、`--root` のリポジトリのプールで done の学びごとに、適用の前と後に同じ `pattern` の事例が何件起きたかを出す（`--text` は表）。
適用日は、プールの一件を done にした日付（`updated` のローカル時刻の日付）である。`commit` の SHA からは引かない。履歴を畳むと、古い commit は読めなくなるためである。事例は `cases` と同じく事例 id の日付で数え、取り消した事例を除く。事例の日付は日単位なので、適用日と同じ日の事例は前とも後とも分けずに数える。
見た日数は、取り消していない全事例の最も新しい日付から適用日を引いた日数である。抽出の済んでいない期間の事例は後に入らないので、後が 0 件でも、見た日数が小さければ効いた証拠にならない。
適用した後も同じ種類が続く学びは、文を足すのでなく形（道具、テスト）を変えるかを人間が決める材料にする。

## 4. 保留している拡張

次の二つは、要件にあるが作っていない。
事例に現れた誤りは会話の上の誤り（返答の言語、依頼の取り違え）が大半で、マージやブランチの書き換えのような危ない操作の誤りが無いので、個別の学びで直して再び起きるかを見ている。
足すかは、`tools/learning/metrics` の数と事例で決める。学びにする事例の件数の閾値（同じ種類の事例が二件）も、同じときに見直す。

### 盲検評価、回帰評価、刈り込み（H-I6、H-I11、H-I8）

- `gori/learning/evals/<id>/` に、事例から作った課題（元の事例の id、依頼文、対象リポジトリの状態、採点基準）を置く。
  採点基準は採点者にだけ渡し、課題は `gori/learning/` の下なのでマシンの手元に残る。
- `tools/learning/eval` を作る。
  候補の版ごとに一時的な worktree で `claude -p --plugin-dir` を実行し、候補の名前を伏せて、作業者とは別の Claude モデルに採点させる。
  手順に従ったかは、判断の記録の step 行と会話の記録上の読み込みから判定する（評価の会話は `sdk-cli` なので抽出には入らない）。
- 知識ファイルを変えたコミットでは全課題を再実行し、前の版と比べる。
- 刈り込みの棚卸しは、人間の依頼で `procedures/prune` に従って手で行う。一定期間使われていない知識ファイルを、`tools/records/usage` の結果からプールに削除候補として自動で起票する道具は、まだ無い。

終わりの条件は、手順を一つわざと消した版を、`tools/learning/eval` が回帰として検出することである。

### 道具による強制（H-E10、H-E7、H-I7、H-K5）

- 無人の作業に限った強制は、ここでの見送りと分けて、3 章「自律起動」で決めた。以下は、人間が見ている作業を含む強制である。
- 被害の大きい操作から順に、強制の道具を書く。
  最初は、マージとブランチの書き換えの前の確認と、PR が準備完了かの判定であり、どちらも状態が不明なら拒む側に倒れることをテストで示す。
  入口として、main の先端を含まない commit のレビューを `review` が断る形がある（3 章「レビューの範囲と E2E」）。
- 3 章で防がないとした意図的な回避を、道具で塞ぐ必要があるかを判断する。
- 利用者ごとの上書き（H-K5）を作る。
  差分は既定の手順書の文言を引用して位置を指定し、引用が見つからなければ検査が報告する。
- 検証の仕組みを保守する手順（H-I7）を書く。

終わりの条件は、それぞれの道具が、状態の不明な入力で危険な操作を拒むテストを持つことである。

## 5. 残る判断

- 取りこぼしを拾う定期の起動を足すかは決めていない。
  セッションを終えないまま会話の記録の保存期間を過ぎると、その会話は読まれずに消える可能性があるので、`tools/learning/metrics` の数で取りこぼしが見えたら足す。
